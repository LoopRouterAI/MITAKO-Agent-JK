# Research: 0714 反馈根因与设计决策

## 多角色对抗结论

本轮以二次元消费者、客服主管、产品经理/CGO、架构安全、前端体验、视觉审核和 QA 七种视角交叉审查。共同结论是：客户要验收的不是“能生成客服语气文本”，而是由统一业务事实驱动的客服、审核、人工和运营服务系统。

## 根因决策

### 决策 1：建立统一 ServiceCase

当前用户、订单、审核任务和人工会话分别由不同前后端状态维护，缺少共同案例标识。新增统一案例语义，所有查询和展示至少绑定 `user_id + session_id + case_id`，订单和审核任务必须校验归属。

### 决策 2：业务意图优先，订单号只做实体提取

订单号不是物流意图。先识别抽赏、未成年人退款、商品有伤、库存等业务语义，再把订单号作为实体交给相应 SOP。

### 决策 3：三种人工状态分离

材料低置信需人工复核、补偿或退款需业务审批、用户沟通需人工接管是三件不同的事。只有用户明确要求并同意、L5 高风险、法律升级或敏感账户操作才进入真实会话转接。

### 决策 4：一轮一个主卡片

卡片是行动入口，不是日志。编排器根据本轮问题选择一张主卡；普通问答和一句话请求不发卡。后台事件仍完整记录，但不全部推给用户。

### 决策 5：审核结果是业务事实

审核任务必须持久化状态、置信度、失败阶段、成本和报告 URL，并能按用户/订单/案例查询。客服 Agent 不再仅凭对话记忆描述“正在审核”。

### 决策 6：可配置密集抽帧是第一层质量旋钮

支持 0.2/0.5/1/2 FPS 和最大帧数。质量提升第二层包括场景化证据要求、多轮局部重采样、连续性检查、结构化业务上下文和人工抽检。543MB 级视频在生产应优先经对象存储与云转码；当前 POC 提供契约和明确失败边界，不伪装已接入七牛云。

### 决策 7：回归标签严格隔离

`sample_labels.json` 只在模型返回后评估，不进入 System Prompt、用户 Prompt、附件描述或业务上下文。报告记录未发送字段。

## 演示与联调边界

### 当前可演示

- 本地 Mock 用户、订单、商品、审核任务和人工队列。
- 三类视觉审核入口、异步任务状态、报告与回归评测。
- 用户端、坐席台、运营后台的端到端 POC。

### 必须甲方联调

- 企微/飞书消息、群和身份映射。
- CRM/CDP 用户分层与标签。
- 商品、SKU、库存、活动和抽赏规则。
- 订单、物流、支付、退款、履约写操作。
- 甲方客服队列、工单、坐席和质检系统。
- 对象存储、云转码、CDN、回调签名和网络白名单。
- 电话、短信和隐私授权。

所有上述能力在接入前均标为 `customer_integration_required`。
