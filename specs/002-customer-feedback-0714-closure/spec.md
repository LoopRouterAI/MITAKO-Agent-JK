# Feature Specification: 0714 甲方反馈闭环整改

**Feature Branch**: `002-customer-feedback-0714-closure`

**Created**: 2026-07-14

**Status**: In Progress

**Input**: 0714 人工测试反馈、线上全量自动测试反馈、原始 Word 截图证据及甲方关于可交付、可验收、可回溯、可评估的要求。

## User Scenarios & Testing

### User Story 1 - 同一业务事实贯穿全流程 (Priority: P1)

用户在切换身份、指定订单、上传材料、查询审核进度或进入人工服务时，系统必须始终使用属于当前用户和当前服务案例的订单、审核任务与业务状态，不得出现跨用户、跨订单或跨场景污染。

**Why this priority**: 数据串线会直接破坏客户对系统安全性和业务可信度的判断，是交付阻断项。

**Independent Test**: 连续切换至少三位演示用户，并在每位用户下显式查询不同订单；页面、接口、卡片、文案、人工简报和审核结果中的用户、订单、商品必须完全一致。

**Acceptance Scenarios**:

1. **Given** 当前用户 A 已产生订单卡片和补偿建议，**When** 切换到用户 B，**Then** 用户 A 的消息、卡片、焦点订单、审核任务和人工状态立即失效且不再渲染。
2. **Given** 页面残留焦点订单 X，**When** 用户本轮明确输入订单 Y，**Then** 系统只查询用户拥有的订单 Y；若 Y 不属于当前用户则返回可审计的拒绝结果，不回退到 X。
3. **Given** 审核任务属于订单 Y，**When** 审核完成、失败或低置信度，**Then** 客服对话、坐席简报与审核报告引用同一个任务和订单状态。

---

### User Story 2 - AI 先完成可自动化的业务服务 (Priority: P1)

用户咨询未成年人退款、商品有伤、抽赏规则、SKU 库存、物流节点或上传图片视频时，AI 应先识别真实业务意图、查询可用事实并给出具体回答；审核需要人工复查不等于当前沟通必须转人工。

**Why this priority**: 甲方购买的是可降低人工成本的服务能力，而不是遇到复杂问题就转人工的聊天机器人。

**Independent Test**: 使用 0714 反馈中的订单号、问题和附件复测，确认意图、服务类型、下一动作、回复和卡片均与场景一致。

**Acceptance Scenarios**:

1. **Given** 文本同时包含订单号和抽赏、未成年退款或商品有伤语义，**When** 系统分类，**Then** 业务语义优先于通用物流规则。
2. **Given** 用户上传图片或视频，**When** 未明确要求人工且无高风险，**Then** 系统创建审核任务并反馈审核状态，不将上传动作分类为 VIP 客服请求。
3. **Given** 材料审核处于低置信度人工复查，**When** 用户询问进度，**Then** AI 解释复查原因、当前节点、时效和补充材料，不自动转接对话。
4. **Given** 用户明确要求当前会话转人工并确认，**When** 转接成功，**Then** 页面进入可验证的排队或已接入状态；失败时明确失败原因，不用话术伪装成功。

---

### User Story 3 - 审核服务形成可观测闭环 (Priority: P1)

甲方系统或演示工作台可批量提交商品有伤、发错货、漏发货和未成年人退款材料，异步获得任务状态、证据摘要、结论、置信度、成本、失败原因、人工复核策略和 HTML 报告，并可将结果回写到客服案例。

**Why this priority**: 这是甲方自动化验收和后续 120G 素材迭代的核心服务能力。

**Independent Test**: 通过标准 API 提交单任务与批任务，轮询或回调获取结果，并从用户端、坐席台和报告链接核对同一任务。

**Acceptance Scenarios**:

1. **Given** 单任务包含多个图片和视频，**When** 提交审核，**Then** 每个资产具有独立处理状态，任务汇总结果可追溯到资产级证据。
2. **Given** 视频过大或过长，**When** 进入预处理，**Then** 按可配置抽帧策略执行；超出本地处理边界时返回明确的转码/对象存储接入要求，不静默失败。
3. **Given** 本地人工标签用于回归评估，**When** 调用模型，**Then** 标签和预期答案不得进入模型输入，报告记录未发送字段。
4. **Given** 审核完成、低置信或失败，**When** 用户查询，**Then** 返回真实状态、置信度或失败阶段和报告入口，不只回复“正在核验”。
5. **Given** 未成年人退款五类材料均已识别到，**When** 系统形成审核结论，**Then** 必须继续核对身份年龄、监护关系、承诺书签署主体、订单支付和手机号实名材料之间的视觉字段一致性；仅材料齐全不得直接输出高置信 `positive`。
6. **Given** 跨材料字段存在冲突、不可读或一致性模型调用失败，**When** 聚合结果，**Then** 结论必须降级为 `review` 并回链相关图片编号，不得把权威真伪验证伪装为已完成。
7. **Given** 一致性初审完成，**When** API 或 HTML 展示结果，**Then** 只展示字段类型、匹配状态、原因码和证据图片编号，不展示姓名、手机号、证件号、订单号、付款账号或 OCR 原文。

### User Story 4 - 低噪音、任务导向的交互编排 (Priority: P2)

每轮回复只展示最能推进当前任务的一张主卡片；一句话请求或普通问答不插入流程卡。追问必须回答新增信息，而不是重复上一轮模板。

**Why this priority**: 卡片刷屏和答非所问会显著降低移动端可用性，并掩盖真正业务结论。

**Independent Test**: 对延期发货、抽赏、商品有伤、新用户咨询和一句话请求各连续提问三轮，检查卡片数量、类型和回答增量。

**Acceptance Scenarios**:

1. **Given** 同一轮同时产生补偿、业务动作和物流数据，**When** 编排用户响应，**Then** 最多展示一张与本轮目标最相关的主卡片。
2. **Given** 用户要求一句话结论，**When** 系统响应，**Then** 不插入任何非必要卡片。
3. **Given** 用户追问“卡在哪个环节”，**When** 系统响应，**Then** 明确当前节点、责任方、下一节点与时效，不复述泛化原因。

---

### User Story 5 - 坐席与运营人员获得可用上下文 (Priority: P2)

坐席接手前可看到真实昵称、会员等级、关注级别、用户诉求、订单、审核状态、情绪和建议动作；默认首句不得拼入错误字段。运营人员可查看公开报告风险明细和演示数据状态。

**Why this priority**: 人工协同必须减少重复询问，并让客户看见系统可管理、可审计。

**Independent Test**: 从用户端触发一次真实转接，坐席接手并回复；在运营后台查看对应会话、审核任务、风险明细和数据来源标签。

**Acceptance Scenarios**:

1. **Given** AI 已采集用户和订单上下文，**When** 坐席打开会话，**Then** 简报字段完整且来源可追溯，默认首句为自然可发送文本。
2. **Given** 当前坐席查看队列，**When** 切换本人、可接、全队列，**Then** 展示范围符合角色权限并有明确标签。
3. **Given** 运维扫描发现公开报告风险，**When** 点击风险数量，**Then** 可查看文件、风险类型、严重度和处理建议。

## Edge Cases

- 当前用户显式输入的订单号不存在或属于其他用户时，不得回退到残留焦点订单。
- 用户切换发生在旧请求尚未结束时，旧请求返回的 SSE、卡片、审核结果和人工状态不得写入新用户界面。
- 一个任务含多个大视频时，系统必须逐资产返回预处理状态，部分失败不得伪装整单成功。
- 模型超时、Key 缺失、结构化输出解析失败、报告生成失败必须进入可观察失败状态。
- 审核低置信度、业务动作需审批、用户沟通需人工三种状态必须分离。
- 演示数据未加载、甲方接口未接入或字段缺失时，界面与接口必须明确标记，不生成虚假实时事实。

## Requirements

### Functional Requirements

- **FR-001**: 系统必须用用户、会话、服务案例和订单四级绑定校验所有业务数据。
- **FR-002**: 本轮明确订单引用必须优先于页面焦点订单，并验证订单归属。
- **FR-003**: 切换用户必须使旧异步请求、SSE 事件、卡片、焦点订单、审核任务和人工状态失效。
- **FR-004**: 意图分类必须优先识别抽赏、未成年人退款、商品有伤、SKU 库存等具体业务语义，再使用通用订单/物流兜底。
- **FR-005**: 上传附件不得自动生成“转客服确认”语义；应创建独立审核任务。
- **FR-006**: 材料人工复查、业务审批和会话转人工必须是三个独立状态。
- **FR-007**: 真实转人工必须有 `offered`、`consented`、`queued`、`connected`、`failed`、`closed` 可验证状态。
- **FR-008**: 每轮用户响应最多展示一张主业务卡片；一句话和普通问答默认不展示卡片。
- **FR-009**: 业务卡片类型、服务类型和下一动作必须与当前 SOP 分支一致。
- **FR-010**: 审核服务必须支持多资产单任务、批任务、异步状态、置信度、成本估算、失败阶段、人工策略和 HTML 报告。
- **FR-011**: 抽帧频率必须可配置，支持至少 0.2、0.5、1、2 FPS，并记录实际策略；密集模式最高 2 FPS。
- **FR-012**: 超大媒体必须返回预处理建议和限制；对象存储、云转码或甲方预处理属于待联调能力时必须明确标识。
- **FR-013**: 回归标签不得进入模型请求；每次推理必须记录输入清单与禁止输入清单。
- **FR-014**: 审核结果必须可按用户、订单、案例和任务查询，并回写客服上下文。
- **FR-015**: 坐席简报必须包含用户、等级、关注级别、订单、诉求、审核状态、情绪、历史动作和建议。
- **FR-016**: 运维风险指标必须提供明细与处置建议，不能只展示总数。
- **FR-017**: 所有演示记录必须标记 `data_mode=demo`、`source_system=mitako_fixture`、`integration_status=not_connected`。
- **FR-018**: 所有待甲方提供的真实能力必须在契约和界面中标为 `customer_integration_required`，不得宣称已接入。
- **FR-019**: 发布包必须包含运行自动化验收所需的非敏感样本元数据，并排除真实 Key、数据库隐私数据和临时缓存。
- **FR-020**: 每项甲方反馈必须映射到代码修改、测试证据、验收结果和剩余边界。
- **FR-021**: 未成年人资料审核必须分别输出材料完整性、视觉字段一致性和权威数据验证三层状态；材料完整性不得替代字段一致性。
- **FR-022**: 视觉字段一致性至少覆盖身份与年龄、监护关系、承诺书签署主体、订单与支付、手机号实名归属五项，并返回可回链的图片编号和受控原因码。
- **FR-023**: 身份证真实性、运营商实名状态、平台订单与支付真实性只能在甲方提供权威接口后验证；当前默认策略为 `disabled`，未接入不得伪装已验真，也不得仅因没有该接口强制转人工。甲方显式配置 `required` 后，未完成权威验证才成为强制复审条件。
- **FR-024**: 未成年人资料的一致性调用失败、字段冲突或证据不可读时必须进入人工复核，不得输出自动通过、自动拒绝或退款动作。
- **FR-025**: 模型可在推理时读取字段进行比较，但持久化 API、日志和公开 HTML 只能保留非敏感匹配状态、原因码和证据引用。
- **FR-026**: 商品有伤专项因果通道不得覆盖或丢失主审核通道已经形成的可观察性与补充证据；专项通道只负责主视频逐帧因果事实，主通道负责补充图片及跨来源关联。
- **FR-027**: 报告必须分别输出视频技术时间轴完整性、开箱过程完整性和争议商品连续可观察性，不得用快递包装离镜替代争议商品离镜，也不得把三类状态合并成笼统“不确定”。
- **FR-028**: 商品有伤报告必须明确主视频和补充图片各自看到/未看到的事实、关联状态和证据权重；补充图片未建立同物、同部位和过程关联时，不得单独推翻主视频结论。
- **FR-029**: “完整视频未见主诉损伤”只能由带版本号的显式策略输出 `negative` 分类建议；策略必须支持可见覆盖、必检视角、离镜时长、特写、同物关联、模型置信度和媒体取证阈值配置，并继续禁止自动业务拒绝。
- **FR-030**: 非 AI 媒体取证必须进入规则审计，至少记录执行状态和风险等级；取证不可用或超过策略风险阈值时必须阻断确定性规则结论，且不得把风险信号表述为已证实剪辑。
- **FR-031**: 商品有伤 HTML 报告必须展示审查步骤、主视频/补充证据分层、关键帧图像与时间点、看到/未看到的事实、证据作用、规则未通过条件、置信度与最终结论。
- **FR-032**: 抽帧首尾覆盖只能表述为采样边界覆盖；容器、码流、时间戳与剪辑风险必须引用独立媒体取证，不得把二者合并为“技术时间轴完整”。
- **FR-033**: 自动分类策略必须由服务端按批准版本解析，请求方只能选择已启用 `policy_ref`，不得自行覆盖门槛或关闭媒体取证、连续性和可观察性守卫。
- **FR-034**: 任一补充图片关联状态未解决时不得自动判负；报告必须逐图说明所见事实、同物关联和过程关联，且多视频帧必须按 `video_index + global_frame_index` 回链。
- **FR-035**: 未成年人字段一致性必须覆盖同类材料的全部清晰、部分可读和不可读图片；部分可读、遮挡或不完整图片必须进入覆盖集合并阻断视觉初审通过。
- **FR-046**: 未成年人退款必须按 SOP 五类必交材料输出逐项绿/黄/红状态、证据图片编号和可点击原图；缺 EXIF 只能作为非阻断黄色提示，明确疑似编辑且证据充分时才可生成红色风险和强制复审建议。
- **FR-047**: HTML 首屏必须用绿/黄/红/灰表达支持、不确定、不支持和技术失败，优先展示结论、证据分数、说人话理由和下一步；空的反证/可疑帧区必须折叠或显示“未发现”。
- **FR-048**: 四类场景必须展示各自适用的置信度组成，未成年人报告不得展示损伤、主体可见率等商品场景字段；技术耗时和抽帧强度必须使用客服可理解的中文表述。
- **FR-049**: 未成年人图片审核并发必须独立可配置并有上限，默认不得牺牲图片全量覆盖、逐张恢复、成本统计和供应商失败隔离。
- **FR-036**: 所有场景的公开 API/HTML 必须采用严格字段白名单、标识符脱敏和中性媒体标识；HMAC 签名不能替代内容脱敏。
- **FR-037**: 模型调用即使超时、结构校验失败或分段失败，也必须计入调用数、Token、成本和耗时审计；不得因失败丢失已完成调用的计费信息。
- **FR-038**: 甲方订单快照只能按工单号、场景和标签唯一匹配后同步；审核输入只提取 SKU、名称、规格、应发数量和商品图引用，用户、地址、价格和人工标签不得进入模型。
- **FR-039**: 新订单资料必须按批次、数字工单号和业务场景建立确定性映射；`ticket_` 前缀应标准化，重名、场景冲突、缺快照或不能唯一关联的案例必须隔离并输出原因，不得猜测匹配。
- **FR-040**: 官方商品图不得全量下载。系统只允许在单次审核中按已选订单商品按需读取有限数量的主图，并按引用或内容摘要缓存复用；`all_goods` 只可作为去重后的辅助信息，不得整表进入模型上下文。
- **FR-041**: 相对商品图引用必须通过服务端配置的 CDN 基地址解析，并经过协议、主机白名单、重定向、响应大小、超时、MIME 与文件特征校验；不符合要求的资源必须隔离，且不得访问本机、内网或未批准主机。
- **FR-042**: 官方商品图与用户提交证据必须使用不同证据角色。官方图只用于 SKU、款式、正常外观和应发物基准，不得被表述为用户开箱证据或单独证明用户诉求成立。
- **FR-043**: 官方商品图下载、解码或压缩失败时，审核任务必须保留最小化 SKU 与履约文字基线继续执行，并明确返回引用不可用和能力降级；不得伪造图片已核验，也不得因此把整个批任务伪装为成功或无条件失败。
- **FR-044**: 文件系统路径只用于内部离线导入。标准审核 API 必须接收结构化订单基线和可解析的图片引用或 URL，公共响应与 HTML 不得泄露本地盘符、归档密码、供应商调试信息或人工标签。
- **FR-045**: 离线同步、模型输入和回归评测必须保持隔离；`annotation.json`、`reply.json`、正负目录名及其他人工结论不得进入模型请求，模型输入清单和禁止输入清单必须可审计。
- **FR-046**: 商品有伤必须分开输出伤情存在性、损伤成因和责任倾向；明确可见伤情不得仅因成因或连续性未确定而被覆盖为 `review`，但成因与责任仍须保留独立不确定性。
- **FR-047**: 报告标题、事实结论、证据分数、人工复审等级、流程建议和兼容字段必须由同一 `advisory_assessment` 派生；补件流程不得同时显示“必须人工复审”或“需要 VIP 复核”。
- **FR-048**: 黄金样本标签必须拆分证据事实、责任倾向和历史经营处置；经营弹性、补偿结果、仓库终判和人工标签不得进入模型请求或替代事实标签。
- **FR-049**: 加速但一镜到底的视频不得自动标为剪辑不合格；抽帧覆盖、媒体技术取证、开箱完整性和争议商品连续性必须作为四个独立维度展示。
- **FR-050**: 所有可发送发布物必须只生成到 `dist/`：甲方测试 ZIP、内部研发 ZIP 和独立甲方 HTML；前端重复构建不得删除这些交付物，项目父目录和 `release/` 不得再生成副本。

### Key Entities

- **ServiceCase**: 一次可追踪客服事项，绑定用户、会话、业务类型、订单、审核任务和人工会话。
- **OrderReference**: 当前用户拥有的订单引用及来源，区分本轮显式引用与页面焦点。
- **ReviewTask**: 多资产审核任务，包含场景、资产、预处理、推理、置信度、成本、策略和报告。
- **HandoffSession**: 当前会话人工转接状态及队列、坐席和审计轨迹。
- **CustomerResponsePlan**: 一轮回复的文字目标、主卡片、业务动作与禁止展示内容。
- **DataProvenance**: 数据模式、来源系统、联调状态和更新时间。
