# Feature Specification: 商业级客服 POC 专业化升级

**Feature Branch**: `001-customer-poc-professional-upgrade`

**Created**: 2026-07-05

**Status**: Draft

**Input**: 用户要求在提交甲方审查前，对用户端客服、人工客服工作台、客服管理中心、视觉审核工作台、移动端和运维/报表能力做系统性专业化升级，并先用 SPEC 明确需求、计划和任务。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 客服主管能一眼判断系统是否有价值 (Priority: P1)

甲方客服负责人打开管理中心时，能先看到真实业务指标：排队人数、最长等待、平均排队时长、Agent 处理量、人工处理量、转人工率、视觉审核量、审核耗时和系统可用性。页面允许加载/清空演示数据，并明确标识“演示数据”与“真实接口数据”的边界。

**Why this priority**: 甲方首先判断系统是否懂客服业务、能否服务高排队量场景；如果后台仍是薄表格和空列表，商业价值无法被认可。

**Independent Test**: 打开后台首页和运营报表，点击“加载演示数据”后，主管能在 30 秒内说清楚当前队列压力、人工介入压力和系统健康状态；点击“清空演示数据”后，页面回到可解释空状态。

**Acceptance Scenarios**:

1. **Given** 后台无真实数据，**When** 主管打开管理中心，**Then** 页面展示清晰空状态、演示数据入口和下一步说明，而不是空白或不可点按钮。
2. **Given** 已加载演示数据，**When** 主管进入监管大盘、队列监控、运营报表和运维大盘，**Then** 能看到排队顺序、等待时长、转人工率、审核数量、平均耗时、服务可用率和异常提醒。
3. **Given** 未选择客服人员，**When** 主管点击强制转交，**Then** 系统给出明确提示并阻止提交。

---

### User Story 2 - 一线客服能高效接单、查询、转交和结案 (Priority: P1)

人工客服打开工作台后，能看到更真实的待处理会话列表，每条会话包含客户诉求、等待时长、情绪风险、订单/物流/仓库/清关/投诉线索和建议下一步。客服接手时通过确认框理解责任边界；转交、升级、结案从专用操作区进入，而不是散落在服务记录同级标题位置。

**Why this priority**: 人工客服是 POC 的核心使用者。当前界面队列数据重复、服务记录和操作混层，会让甲方认为系统不懂客服工作。

**Independent Test**: 在人工客服工作台加载演示队列，选择三条不同类型会话，客服能在两次点击内完成“接手并回复”或“升级/转交/结案”路径，且每一步都有明确反馈。

**Acceptance Scenarios**:

1. **Given** 队列中有不同诉求的会话，**When** 客服点击左侧列表，**Then** 中间对话、右侧服务档案和建议动作随会话真实变化。
2. **Given** 会话未接手，**When** 客服点击接手，**Then** 出现确认框说明接手后需要负责跟进、可转交或结案。
3. **Given** 客服需要升级，**When** 从专用“转交/升级”按钮进入，**Then** 能选择高级客服、填写原因，并看到成功或失败提示。
4. **Given** 客服在手机竖屏访问工作台，**When** 查看队列和回复用户，**Then** 队列、对话、服务档案按底部切换或单列布局呈现，按钮触控目标不小于 44px。

---

### User Story 3 - 用户端客服看起来专业且不误导 (Priority: P1)

用户端聊天中的生成式业务卡片必须明确区分“状态摘要”与“可点击操作”。不可点击的信息块不能像按钮；需要用户操作的卡片必须有真实按钮和文案。整体视觉对标视觉审核工作台的明亮工具风格，减少粗黑边和过亮绿色造成的廉价感。

**Why this priority**: 截图中“服务处理进度”卡像按钮但不可点击，会直接破坏用户信任和演示质量。

**Independent Test**: 触发订单咨询、售后建议、转人工、业务处理进度卡片，观察者能分辨哪些只是摘要、哪些可以点击，并且没有英文或内部术语泄漏。

**Acceptance Scenarios**:

1. **Given** AI 输出服务处理进度，**When** 用户看到卡片，**Then** 卡片以只读状态摘要呈现，不出现按钮式双格控件。
2. **Given** 需要用户确认转人工或选择订单，**When** 卡片出现，**Then** 按钮文案明确、可点击且点击后状态更新。
3. **Given** 页面在移动端显示，**When** 用户输入长句或查看卡片，**Then** 文案不溢出、不遮挡、不出现调试/外包/模型渠道信息。

---

### User Story 4 - 视觉审核工作台能融入客服工单流程 (Priority: P2)

人工客服可以从三大审核任务的独立入口直接进入对应审核流程，也可以从工单上下文发起或补充审核材料。系统应让客服理解：理想情况下订单、用户、物流、历史投诉和材料来自甲方接口；手动模式用于补传视频、纠正诉求、补充图片和复核异常。

**Why this priority**: 视觉审核是甲方 60% 人力痛点，但当前工作台更像能力展示页，尚未充分体现客服工单效率提升。

**Independent Test**: 打开三个子路径或入口，分别进入开箱视频、商品有伤、未成年人资料审核；客服能理解要上传什么、哪些字段未来来自接口、如何补件、如何把报告用于工单处理。

**Acceptance Scenarios**:

1. **Given** 客服只负责商品有伤审核，**When** 访问商品有伤专用入口，**Then** 页面直接进入对应任务，不要求先理解总览页或场景下拉。
2. **Given** 用户传错视频或订单选错，**When** 客服在审核任务里补充材料，**Then** 页面说明补充材料会作为新的证据包用于复核。
3. **Given** 审核完成，**When** 客服查看报告，**Then** 报告优先展示结论、置信度、证据链、缺失材料和人工动作建议。

---

### User Story 5 - 团队能持续迭代而不被旧设计污染 (Priority: P2)

研发、测试和项目负责人需要有一份当前有效的升级规格、计划、任务和经验沉淀，明确哪些旧 Companion/角色扮演/冒险模式已经封存，哪些 Mock 只用于甲方未接接口前的演示。

**Why this priority**: 项目上下文已经多轮变更，旧文档和旧代码会误导后续迭代。

**Independent Test**: 新研发只阅读本 spec、plan、tasks 和内部文档首页，就能解释当前 POC 的产品边界、演示数据边界、落地顺序和验收方式。

**Acceptance Scenarios**:

1. **Given** 新研发接手，**When** 阅读本轮文档，**Then** 能区分当前客服系统与已封存 Companion/角色扮演能力。
2. **Given** 文档中出现过旧认知，**When** 更新本轮经验沉淀，**Then** 删除或归档已不适用内容，不在 Docs 中堆积垃圾文件。

### Edge Cases

- 没有演示数据且无真实接口时，页面必须展示“当前没有数据”和“如何加载演示数据/接入甲方接口”，不能让按钮静默失败。
- 后台强制转交未选择目标客服时，必须阻止并提示。
- 低权限账号不能配置补偿额度或审批模板，只能查看或发起符合权限的申请。
- 移动端屏幕窄时，人工工作台不能三栏硬挤；必须有清晰的队列、对话、档案切换方式。
- 视觉审核任务材料不足或 URL 不可读时，必须说明下一步补什么材料。
- 所有面向甲方的页面不得暴露模型供应商、Key、内部 Prompt、调试参数、外包等信息。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须统一用户端、人工工作台、管理中心和视觉审核工作台的视觉语言，主色对标视觉审核工作台的明亮工具风格，并降低粗黑描边和过亮绿色的占比。
- **FR-002**: 系统必须把不可点击的业务卡片渲染为只读状态摘要，把可点击动作渲染为明确按钮。
- **FR-003**: 管理中心必须提供演示数据加载/清空入口，并在页面上标识当前是演示数据、真实数据还是空状态。
- **FR-004**: 人工客服工作台必须展示更真实的多类型会话队列，每条会话至少包含诉求摘要、状态、等待时长、风险等级和建议下一步。
- **FR-005**: 人工客服工作台必须支持接手确认、回复、专用转交/升级入口、结案入口和失败提示。
- **FR-006**: 人工客服工作台必须在移动端提供单列或分段视图，让客服可以在移动环境完成查看队列、回复、转交和结案。
- **FR-007**: 管理中心队列监控必须展示排队顺序、已等待时间、当前处理人、目标客服选择和强制转交反馈。
- **FR-008**: 服务记录必须支持点击后在固定详情区查看完整消息、业务事件和处理动作，而不是只追加到列表底部。
- **FR-009**: 服务质检必须说明功能目的，并至少展示待复盘、需跟进、已通过三类状态或空状态引导。
- **FR-010**: 补偿审批必须区分普通客服发起、主管审批、超级管理员配置额度/模板的权限边界。
- **FR-011**: 运营报表必须从表格升级为客服 Leader 能读懂的指标视图，至少包含 Agent 处理量、人工处理量、转人工率、最长等待、平均排队时长和结案/待处理趋势。
- **FR-012**: 7×24 运维必须提供简单可靠的健康 BI，展示主系统、人工台、视觉审核、模型调用的可用性、延迟、连续稳定天数和告警数量。
- **FR-013**: 视觉审核工作台必须支持三大审核任务的直接入口，并说明哪些字段未来来自甲方接口、哪些字段当前由客服手动补充。
- **FR-014**: 视觉审核报告必须优先展示结论、置信度、证据链、缺失材料和人工动作建议，减少技术噪音。
- **FR-015**: 系统文档必须沉淀本轮需求变化、设计取舍、踩坑经验和验收方式，并清理明显过旧且会误导当前客服 POC 的文档入口。
- **FR-016**: 面向甲方/用户的文案必须尽量中文化、低理解成本，避免客服人员需要理解英文、内部模型术语或工程术语。

### Key Entities

- **演示数据状态**: 当前后台是否加载演示数据、加载时间、数据覆盖范围、清空动作。
- **客服会话**: 用户诉求、当前状态、等待时长、风险等级、处理人、历史消息、业务事件、结案结果。
- **客服人员**: 一线客服、高级客服、主管、超级管理员；包含技能、队列权限和审批权限。
- **服务记录**: 会话详情、消息、业务动作、质检状态、转交/升级记录、结案原因。
- **补偿申请**: 发起人、金额、原因、审批等级、状态、审批人、审计记录。
- **运营指标**: 排队、接入、升级、转交、结案、审核、可用性、延迟、告警。
- **视觉审核任务**: 审核类型、证据包、来源工单、补充材料、结论、置信度、人工动作建议。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 甲方客服负责人在 3 分钟内能通过后台首页和报表说出当前队列压力、人工介入压力和系统健康状态。
- **SC-002**: 人工客服在演示数据下选择任意会话后，2 次点击内能完成接手并发送一条回复，或进入转交/升级/结案路径。
- **SC-003**: 用户端所有不可点击业务卡片经目测不再像按钮，且至少 3 类卡片通过手工验证无误导交互。
- **SC-004**: 移动端 390px 宽度下，人工工作台的队列、对话、服务档案和操作区均可访问，无横向溢出，主要按钮触控目标不小于 44px。
- **SC-005**: 管理中心空状态、演示数据状态和强制转交失败状态均有可见中文反馈，不再静默失败。
- **SC-006**: 视觉审核三类任务均可通过独立入口直达，客服无需先操作场景下拉即可开始对应审核。
- **SC-007**: 本轮文档包含 spec、plan、tasks、经验沉淀，并且 README/文档首页能指向当前有效版本。

## Assumptions

- 本轮不接入甲方真实生产订单、仓库、财务、退款或私域系统；相关能力通过演示数据和接口契约表达。
- 本轮不新增重型前端依赖，优先复用 React、Tailwind、Lucide 和现有组件。
- 本轮先做商业 POC 可信度提升，不一次性重写全部后台架构。
- 健康监测参考 Relay Pulse 的“真实调用、可用率、延迟、趋势”思路，但不引入完整外部系统。
- Companion、角色扮演、文字冒险能力保持封存，不进入当前客服 POC 验收范围。
