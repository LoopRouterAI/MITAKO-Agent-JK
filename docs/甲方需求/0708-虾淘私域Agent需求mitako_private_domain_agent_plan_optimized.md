# 虾淘私域用户运营 Agent 生产级规划文档（优化版）

> 文档定位：面向产品、研发、算法、运营、客服、数据与项目管理团队的生产级 Agent 规划文档。  
> 适用范围：虾淘 1 万+企业微信私域大群、App / 小程序商品与活动承接、客服 Agent 与售后系统协同。  
> 优化方向：不做商务说服，不写报价包装；所有设计均围绕虾淘真实私域运营痛点、产研可开发性、生产安全性、运营可复盘性展开。  
> 版本：v2.0 优化版  
> 日期：2026-07-08

---

## 0. 本版优化说明

上一版文档已经覆盖了私域运营 Agent 的总体架构、谷子词典、吃谷雷达、舆情预警、企微接入、记忆系统、Prompt、后台、指标和路线图。本优化版做以下调整：

1. 删除或弱化偏商务说服、报价、商业包装类内容。
2. 强化“客户真实痛点 -> 产品需求 -> 系统能力 -> 运营动作 -> 数据回写”的完整链路。
3. 将“用户分层”前置为“群资产分层”，因为虾淘首期最小运营单元是 1 万+社群，而不是单个用户。
4. 将三大核心场景拆成可开发需求：谷子词典、吃谷雷达、舆情与客诉治理。
5. 明确 Agent 能做什么、不能做什么，避免过度自动化带来客诉和合规风险。
6. 增加企微权限三档降级方案，确保不同接入条件下仍可落地。
7. 增加模型调用分层、记忆系统边界、Guardrail、异常处理、灰度测试和验收标准。
8. 增加与既有客服 Agent 的接口关系，避免私域 Agent 与客服系统形成两个孤岛。
9. 将阶段规划改为“群级 MVP -> 用户级精细化 -> 全量智能运营闭环”的产研路径。

## 1. 项目定位

### 1.1 项目不是 AI 客服，也不是抽奖小程序

虾淘已经具备自己的 App、小程序、抽奖活动、分享激活码、活动发布等业务能力。私域用户运营 Agent 不应重复建设这些系统。

本项目的定位是：

**围绕虾淘 1 万+企业微信私域群，将群内非结构化聊天、IP 兴趣、角色偏好、蹲谷需求、活动反馈、负面情绪和客服风险，转化为可识别、可触达、可预警、可复盘的群运营系统。**

因此它不做：

- 抽奖概率系统；
- 激活码生成系统；
- 支付交易系统；
- 奖池管理系统；
- 订单履约系统；
- 完整客服工单系统；
- 纯聊天机器人；
- 单纯群发机器人。

它重点做：

- 群资产画像；
- 群内基础知识问答；
- 新品、开赏、补货、隐藏款事件推送；
- IP / 角色 / 品类兴趣识别；
- 群内互动与活动种草；
- 客诉情绪监控；
- 高风险群自动禁推；
- 群内安抚与私聊引导；
- 与客服 Agent 协同；
- 群级与活动级运营复盘。

### 1.2 系统核心目标

系统目标不是让 Agent “像人一样聊天”，而是让私域群真正进入可运营状态。

| 目标 | 具体含义 | 关键系统能力 |
|---|---|---|
| 让群资产可识别 | 知道每个群的 IP、活跃、转化、风险、疲劳状态 | 群画像、群标签、群健康度 |
| 让活动触达更精准 | 不再所有群统一发链接，而是按群兴趣和风险状态推送 | 商品事件、群匹配、频控 |
| 让新手问题可自动消化 | 术语、玩法、活动规则可低风险回答 | 谷子词典、RAG、问答边界 |
| 让高意向需求被捕捉 | 用户“蹲”“求补”“想要”可沉淀成运营信号 | 许愿池、蹲谷雷达、标签写入 |
| 让群内舆情可提前发现 | 不发货、退款、吞烫、霸王条款等负面能尽早识别 | 关键词、情绪、多人数共振、预警 |
| 让营销动作可控 | 高风险群、疲劳群、投诉群不再继续硬推 | 禁推、降频、Guardrail |
| 让运营可复盘 | 每次推送、互动、安抚都能看到结果 | 点击、下单、情绪、群状态回写 |

### 1.3 产研建设原则

1. **群级优先，用户级逐步深入**  
   首期先解决 1 万+群无法精细管理的问题。单用户千人千面留到二期，避免过早拉高数据接入和合规复杂度。

2. **规则优先，模型增强**  
   高频、低风险、可规则化的问题用规则和知识库解决；复杂情绪、语义判断和内容生成再调用大模型。

3. **自动识别，谨慎发送**  
   系统可以自动识别风险、自动生成建议，但对营销群发和高风险安抚必须有审核、频控和禁推策略。

4. **业务动作闭环优先于内容生成**  
   AI 不是泛泛生成文案，而是要触发具体业务动作：推送、禁推、转客服、打标签、复盘。

5. **可观测、可回滚、可降级**  
   任一自动化动作都需要日志、状态、责任人、回滚机制和人工接管。

## 2. 虾淘私域场景与问题定义

### 2.1 当前私域链路

虾淘当前私域大致链路可以抽象为：

公域 / App / 小程序 / 活动入口 -> 用户进入企业微信群 -> 群内获取新品、谷子信息和限时抽奖活动 -> 点击小程序或 App -> 参与抽赏、购买、分享获得激活码 -> 等待发货 / 售后 / 退款 -> 回到群内讨论体验。

该链路中，群既是营销触达渠道，也是用户互相影响的公共场域。一旦群里只有活动链接而缺少运营，群会出现两种极端：

- 正常情况下：用户沉默、链接被忽略、兴趣和需求没有被识别；
- 出问题时：售后情绪集中爆发，群从福利群变成维权群。

### 2.2 虾淘场景的产研判断

| 客户真实场景 | 产研判断 | Agent 产品方向 |
|---|---|---|
| 1 万+群无人精细管理 | 不能依赖人工逐群维护 | 群资产模型、群健康度、群策略推荐 |
| 当前主要发小程序链接 | 活动触达粗放 | 基于 IP / 角色 / 商品事件的精准推送 |
| 小程序用户占 3-4 成，App 用户近 6 成 | 承接链路不能只围绕小程序 | 小程序链接 + App Deep Link 双承接 |
| 用户关注新品、隐藏款、补货、稀有款 | 普通电商营销话术无效 | 吃谷雷达、蹲谷提醒、许愿池 |
| 群内有大量新手 | 黑话和规则门槛高 | 谷子词典、玩法问答、新手引导 |
| 平台存在不发货客诉 | 群内容易演变为群体投诉 | 舆情监控、禁推、私聊分流、客服联动 |
| 群聊有大量偏好数据 | 当前没有结构化沉淀 | IP / 角色 / 品类 / 活动兴趣标签 |
| 抽奖小程序已经很强 | AI 不应重做活动能力 | AI 做活动前种草、活动中提醒、活动后复盘 |

### 2.3 核心痛点拆解

#### 2.3.1 群资产不可见

目前 1 万+群的真实状态可能存在巨大差异：有的群高活跃高转化，有的群只看不买，有的群已接近投诉群，有的群可能对某个 IP 高度集中。但如果没有群级画像，运营只能统一发活动，难以判断该发什么、不该发什么、什么时候发、发给谁。

#### 2.3.2 活动触达不匹配

新品、开赏、隐藏款、补货这类事件对谷圈用户很重要，但如果所有群统一发，容易出现三类问题：

- 用户感兴趣的群没有及时收到；
- 无关群收到过多打扰；
- 高风险群仍被营销刺激，导致负面反噬。

#### 2.3.3 群内新手问题没有被低成本消化

谷圈术语和平台规则对新用户存在门槛，例如出荷、大赏、小赏、再贩、预售、清关、补款、抱盒、隐藏款等。如果基础问题长期无人回答，新人会流失；如果全部由人工客服回答，又会占用客服资源。

#### 2.3.4 售后情绪容易公共化

不发货、退款、吞烫、霸王条款等问题如果在群里被多人接话，问题会从单个订单变成群体情绪。私域 Agent 的价值不是在群里“解释清楚所有订单”，而是尽早识别情绪聚集，把公共讨论转为一对一处理，并同步客服和主管。

#### 2.3.5 群聊反馈没有反哺业务

用户在群里说“想要某角色”“蹲补货”“这个 IP 还有吗”“又没抢到”等，都是真实需求信号。当前如果没有结构化沉淀，这些信号无法反哺选品、补货、活动配置和推送策略。

## 3. 产品目标与非目标

### 3.1 产品目标

1. **建立群资产系统**  
   将 1 万+群从“群列表”变成可运营的群资产池。

2. **建立商品事件分发系统**  
   将 App / 小程序里的新品、开赏、补货、隐藏款、库存低位等事件，转化为按群匹配、按风险控制、按频率约束的推送任务。

3. **建立群内低风险问答系统**  
   自动解答术语、玩法和活动规则问题，减少小白流失和人工重复回答。

4. **建立群内舆情治理系统**  
   对不发货、退款、吞烫、霸王条款、维权、投诉等高危信号进行识别、分级、预警、禁推和客服联动。

5. **建立群运营数据闭环**  
   记录每个群的推送、点击、下单、互动、负面、转客服、禁推、恢复状态，支撑后续策略优化。

### 3.2 非目标

#### 3.2.1 不重做抽奖活动系统

Agent 不负责抽奖概率、奖池逻辑、激活码生成、支付和履约。它只负责围绕现有活动做群内运营和转化辅助。

#### 3.2.2 不替代客服 Agent

订单查询、退款审核、补偿发放、售后判责等仍由客服 Agent 或客服系统处理。私域运营 Agent 只负责识别问题、安抚、引导私聊、创建客服任务和回写群风险状态。

#### 3.2.3 不做无限制自动群发

所有营销类推送都必须受群状态、风险等级、疲劳度、频控、活动优先级和运营配置约束。高风险群必须自动禁推。

#### 3.2.4 不在群内公开处理订单纠纷

群内不能公开索要订单号、讨论退款金额、判定责任或承诺发货时间。订单类问题必须引导到私聊或客服系统。

#### 3.2.5 不参与争辩

面对攻击、质疑、投诉和维权组织，Agent 只能识别、安抚、引导、预警，不能反驳用户、甩锅、争论规则或继续营销。

## 4. 总体系统架构

### 4.1 逻辑架构

系统由以下层级组成：

1. **接入层**  
   企业微信群消息、商品事件、活动事件、点击事件、订单回传、客服状态回写。

2. **事件层**  
   将群消息、商品变化、用户点击、客诉信号统一抽象为事件，进入消息队列和任务调度。

3. **理解层**  
   对消息、商品、群状态、用户行为进行意图识别、IP 识别、角色识别、情绪识别、风险判断。

4. **决策层**  
   判断是否回答、是否推送、推给哪些群、是否禁推、是否转客服、是否升级主管。

5. **生成层**  
   生成群内回答、商品推送文案、安抚话术、客服摘要、运营日报。

6. **审核层**  
   对所有将要发送到群内的内容做 Guardrail 审核，拦截敏感承诺、违规营销、争辩话术、错误规则。

7. **执行层**  
   发送群消息、创建客服任务、写入标签、触发禁推、推送主管预警。

8. **数据层**  
   群画像、用户画像、商品事件、知识库、向量库、会话日志、风险记录、推送归因。

9. **后台层**  
   群资产驾驶舱、吃谷雷达工作台、谷子词典、舆情预警、客服协同、许愿池、运营复盘。

### 4.2 技术选型建议

| 系统层 | 推荐选型 | 说明 |
|---|---|---|
| 后端服务 | Python FastAPI / Node.js NestJS | 与既有 demo 技术栈和 Agent 服务生态适配 |
| 任务编排 | LangGraph / 自研状态机 | 适合多 Agent 路由、状态持久化和人工接管 |
| 消息队列 | Kafka / RabbitMQ / Redis Stream | 支撑万群消息和商品事件异步处理 |
| 主数据库 | PostgreSQL | 存储群、用户、商品、推送、任务、风险记录 |
| 缓存 | Redis | 频控、冷却、滑动窗口、临时状态 |
| 向量库 | OpenViking / Milvus / Qdrant | 术语、规则、SOP、历史案例检索 |
| 搜索 | Elasticsearch / OpenSearch | 高危词、群消息、日志检索 |
| 模型网关 | LiteLLM / 自研 Model Gateway | 统一模型路由、限流、降级、成本统计 |
| 观测 | Langfuse + Prometheus + Grafana | 追踪模型调用、延迟、成本、失败率 |
| 后台前端 | React / Vue | 复用当前管理后台能力 |

### 4.3 为什么不能所有消息都走大模型

虾淘有 1 万+群，如果每条群消息都直接进入大模型，会产生四个问题：

1. 成本不可控；
2. 延迟不可控；
3. 并发峰值不可控；
4. 错误回复风险不可控。

因此生产架构必须采用分层处理：

规则快筛 -> 轻量分类 -> RAG / 小模型处理 -> 大模型复核 -> Guardrail 审核 -> 执行动作。

## 5. 企业微信接入与权限分级

### 5.1 接入能力需要先确认

产研启动前必须确认企业微信侧是否具备以下能力：

| 能力 | 用途 | 对系统影响 |
|---|---|---|
| 客户群消息读取 | 群内问答、舆情监控、标签更新 | 核心能力 |
| 客户群消息发送 | 自动问答、推送、安抚 | 核心能力 |
| 群成员识别 | 用户标签、蹲谷记录、私聊引导 | 影响用户级运营 |
| 外部联系人 ID | 连接企微与 App / 小程序用户 | 影响 OneID |
| 会话存档 | 可靠采集群消息和证据 | 影响合规与舆情追溯 |
| 群发能力 | 活动推送 | 影响吃谷雷达 |
| 私聊触达能力 | 客诉分流、蹲谷提醒 | 影响二期用户级能力 |
| 链接点击回传 | 归因 | 影响效果复盘 |

### 5.2 三档落地方案

#### A 档：完整自动化能力

条件：可接收群消息、可发送群消息、可识别外部联系人、可接入会话存档、可回传点击和订单。

可实现：

- 谷子词典自动问答；
- 实时舆情监控；
- 吃谷雷达自动或半自动推送；
- 群风险禁推；
- 用户偏好沉淀；
- 私聊分流；
- 完整归因复盘。

#### B 档：半自动能力

条件：不能完整实时读群，但可以群发、可导出部分数据、可后台审批。

可实现：

- 商品事件推送建议；
- 运营审核后一键群发；
- 群级标签半自动更新；
- 舆情依赖关键词、导出数据或人工标记；
- 活动复盘和策略建议。

#### C 档：低权限能力

条件：不能读群，也不能自动发群，只能由运营手动执行。

可实现：

- AI 运营助手；
- 推送文案生成；
- 谷子词典知识库；
- 活动策略推荐；
- 手动复盘；
- 客服知识辅助。

### 5.3 接入原则

1. 不使用不稳定或不合规的 Hook 方案作为生产主方案。
2. 如果甲方已有企微服务商或 SCRM，需要优先评估开放接口。
3. 群消息采集需要明确授权、留存周期和可见权限。
4. 所有自动发送动作必须有日志和追踪 ID。
5. 高风险功能必须支持关闭和降级。

## 6. 群资产模型

### 6.1 为什么群资产模型优先于用户画像

虾淘首期面对的是 1 万+大群。若一开始就追求单用户千人千面，会遇到用户身份映射、隐私授权、消息采集、订单关联、模型成本等复杂问题。

因此一期优先建立群级运营系统：先判断“这个群是什么群、适合什么内容、现在能不能推、风险如何、转化如何”。

### 6.2 群基础字段

| 字段 | 说明 |
|---|---|
| group_id | 企业微信群唯一 ID |
| group_name | 群名称 |
| owner_id | 群主 / 客服账号 |
| member_count | 群人数 |
| created_at | 创建时间 |
| source_channel | 入群来源 |
| group_type | IP 群、活动群、泛兴趣群、售后群等 |
| linked_activity_id | 关联活动 ID，可为空 |
| linked_ip_id | 关联 IP ID，可为空 |
| status | 正常、观察、疲劳、高风险、禁推、解散等 |

### 6.3 群动态指标

| 指标 | 说明 | 计算周期 |
|---|---|---|
| daily_message_count | 日消息数 | 日 |
| daily_active_members | 日发言人数 | 日 |
| ai_reply_count | Agent 回复次数 | 日 |

### 6.4 群标签体系

| 标签类型 | 示例 |
|---|---|
| IP 标签 | 蓝色监狱、原神、排球少年、名侦探柯南 |
| 角色标签 | 凪诚士郎、洁世一、魈、流萤 |
| 品类标签 | 吧唧、亚克力、流麻、色纸、盲盒、一番赏 |
| 活跃标签 | 高活跃、中活跃、沉默 |
| 转化标签 | 高点击高下单、高点击低下单、低点击、未知 |
| 风险标签 | 正常、轻度不满、高风险、维权风险、禁推 |
| 疲劳标签 | 可推、谨慎、降频、暂停 |
| 用户结构 | 新手多、老玩家多、高价值用户多、售后用户多 |
| 内容偏好 | 抽赏、补货、隐藏款、福利、晒谷、许愿 |

### 6.5 群分层策略

| 群类型 | 特征 | 主要目标 | Agent 策略 |
|---|---|---|---|
| 高活跃高转化群 | 发言多、点击高、下单高 | 放大转化 | 优先推新品、隐藏款、限时活动 |
| 高活跃低转化群 | 聊得多但买得少 | 从氛围到转化 | 多互动、多种草、少硬广 |
| 低活跃高转化群 | 话少但买 | 精准触达 | 低频高价值推送 |
| 低活跃低转化群 | 没人说话也不点 | 唤醒或降权 | 低频测试，避免浪费推送 |
| IP 垂直群 | 某 IP 浓度高 | IP 深运营 | 只推强相关 IP 内容 |
| 泛兴趣群 | 兴趣分散 | 热点运营 | 推热榜、福利、通用活动 |
| 新群 | 数据不足 | 建立画像 | 先观察，轻互动，低频推送 |
| 高风险群 | 负面多、售后集中 | 控风险 | 禁推营销，转客服，主管预警 |
| 投诉恢复期群 | 刚处理完风险 | 修复关系 | 暂停营销，仅保留服务信息 |

### 6.6 群健康分

群健康分用于判断群是否适合继续营销。建议由以下因子组成：

- 活跃度；
- 点击率；
- 下单率；
- 负面消息比例；
- 退群率；
- 投诉用户数；
- 最近营销频率；
- 最近客服处理状态；
- 最近风险等级。

群健康分不应只追求活跃。高活跃但高负面，属于风险群，不是优质群。

## 8. 核心事件流设计

### 8.1 群消息事件流

群消息进入系统后，不直接交给大模型回复，而是按以下流程处理：

1. 消息采集；
2. 清洗、脱敏、去重；
3. 规则快筛：高危词、术语词、IP 词、角色词；
4. 意图分类：术语、活动、商品、物流、售后、投诉、闲聊；
5. 风险判断：情绪、人数、时间窗口、群状态；
6. 进入对应处理链路：问答、标签写入、舆情预警、客服转接或忽略；
7. 写入群画像和用户画像；
8. 记录日志。

### 8.2 商品事件流

1. App / 小程序商品系统产生事件；
2. 系统解析事件类型：新品、开赏、补货、隐藏款、库存低位、活动开始、活动结束；
3. 解析商品标签：IP、角色、品类、稀有度、库存、价格、活动时间；
4. 查询群画像；
5. 排除高风险群、疲劳群、禁推群；
6. 计算群匹配分；
7. 生成推送任务；
8. 运营审核或自动发送；
9. 发送后追踪点击、订单、情绪和退群；
10. 回写群画像和活动复盘。

### 8.3 点击与转化事件流

1. 群内推送链接带上 group_id、event_id、campaign_id、template_id；
2. 用户点击后跳转小程序或 App；
3. 交易系统回传下单或支付结果；
4. 系统归因到群、商品事件、IP、文案模板；
5. 更新群转化标签；
6. 更新用户兴趣与价值标签；
7. 进入复盘中心。

### 8.4 客诉事件流

1. 群内出现不发货、退款、吞烫、霸王条款等信号；
2. 规则层触发候选风险；
3. 模型结合上下文判断风险等级；
4. 若达到 L2 以上，自动暂停该群营销；
5. 生成群内安抚建议；
6. 创建客服任务；
7. 主管预警；
8. 客服处理状态回写；
9. 风险降级后恢复或继续观察。

### 8.5 许愿与蹲谷事件流

1. 用户在群里表达“想要”“蹲”“求补”“有没有”；
2. 系统识别 IP、角色、品类、商品；
3. 写入用户蹲谷意向；
4. 聚合为群许愿池和全局 IP 热度；
5. 补货或上新时触发吃谷雷达；
6. 反哺选品、活动和推送策略。

## 9. 核心场景一：谷子词典与日常问答

### 9.1 场景目标

谷子词典的目标不是“陪聊”，而是降低新手理解门槛、减少客服重复劳动、避免基础问题在群内无人回应。

### 9.2 知识库分类

| 知识类别 | 示例问题 | 数据来源 | 回答策略 |
|---|---|---|---|
| 谷圈术语 | 什么是出荷、再贩、大赏、小赏、痛包、吧唧 | 运营维护词典 | 可自动回答 |
| 平台玩法 | 怎么抽赏、激活码怎么用、分享怎么参与 | 小程序规则、活动规则 | 可自动回答，需版本控制 |
| 物流常识 | 清关要多久、预售多久发 | 平台物流规则 | 谨慎回答，避免承诺具体时效 |
| 活动规则 | 活动什么时候结束、怎么抽 | 活动配置接口 | 可回答，但必须引用当前版本 |
| 售后边界 | 能不能退、能不能改地址 | 售后 SOP | 只做原则解释，复杂问题转客服 |
| 订单问题 | 我的订单为什么没发 | 订单接口 / 客服系统 | 群内不处理，转私聊 |
| 负面投诉 | 你们是不是不发货 | 舆情模块 | 不进入知识问答，转安抚和预警 |

### 9.3 意图分类

谷子词典的入口必须先做意图分类，避免把投诉误当知识问答。

| 意图 | 处理方式 |
|---|---|
| 术语解释 | RAG 回答 |
| 玩法说明 | RAG 回答 |
| 活动规则 | 当前活动规则回答 |
| 商品咨询 | 视商品接口回答或引导点击 |
| 物流 / 履约 | 保守回答，必要时转客服 |
| 售后 / 退款 | 原则回答，具体问题转客服 |
| 投诉 / 负面 | 进入舆情链路 |
| 玩梗 / 闲聊 | 多数忽略，必要时轻互动 |
| 攻击 / 辱骂 | 不争辩，记录风险 |
| 需要人工 | 创建客服任务 |

### 9.4 回答边界

#### 可以自动回答

- 术语解释；
- 基础玩法；
- 当前活动规则；
- 如何参与分享；
- 一般物流流程；
- 群内新手引导。

#### 需要谨慎回答

- 发货时效；
- 清关时长；
- 退款条件；
- 售后责任；
- 商品损伤；
- 未成年人退款；
- 账号换绑。

#### 必须转客服

- 具体订单；
- 具体退款；
- 补偿承诺；
- 长期不发货；
- 群体投诉；
- 用户要求曝光或投诉；
- 规则争议。

### 9.5 回复安全规则

禁止：

- 承诺“马上发”；
- 承诺“一定能退”；
- 说“不是我们的问题”；
- 说“规则就是这样”；
- 群内公开索要订单号；
- 对用户情绪进行评价；
- 在群内争辩平台责任。

建议：

- 解释基础概念；
- 使用轻松但不轻浮的语气；
- 涉及订单时引导私聊；
- 对用户焦虑先承认再分流；
- 回答不确定时说明需以订单状态或活动页面为准。

### 9.6 谷子词典 System Prompt 设计

角色：你是虾淘私域群内的“谷子词典助手”，主要负责解答谷圈术语、平台玩法、活动规则和基础问题。你不是客服判责人员，也不是订单处理人员。

核心规则：

1. 只回答你有知识库依据的问题。
2. 术语和玩法可以直接解释，订单和售后必须引导私聊客服。
3. 不得承诺具体发货时间、退款结果、补偿方案。
4. 当用户情绪明显不满时，不继续科普，改为安抚并转客服。
5. 回复应简短、清楚、自然，避免长篇解释。
6. 群内同类问题短时间内不重复刷屏。
7. 如果无法确认，必须说“以活动页面/客服核实结果为准”。

输出要求：

- 先给直接答案；
- 再给一句新手友好解释；
- 涉及平台规则时提醒以当前活动页面为准；
- 涉及订单问题时引导私聊。

### 9.7 产研功能拆分

| 功能 | 一期 | 说明 |
|---|---|---|
| 术语知识库 | 是 | 出荷、大赏、小赏、再贩、吧唧、流麻等 |
| 活动规则知识库 | 是 | 需支持版本管理 |
| 物流规则问答 | 是 | 只做保守解释 |
| 售后边界问答 | 是 | 只做原则说明 |
| 订单查询 | 否 / 视接口 | 一期可转客服 |
| 问答冷却 | 是 | 同群同问题冷却 |
| 未命中问题收集 | 是 | 进入知识库优化 |
| 自动学习新词 | 二期 | 需人工审核后入库 |

### 9.8 验收标准

| 测试项 | 标准 |
|---|---|
| 术语回答准确率 | 抽样问题准确率达到项目约定标准 |
| 活动规则回答 | 必须引用当前活动版本 |
| 售后问题处理 | 不得擅自承诺，必须转客服 |
| 未知问题处理 | 不胡编，记录并转人工或提示无法确认 |
| 刷屏控制 | 同群同类问题有冷却 |
| 安全边界 | 不公开处理订单，不争辩 |

## 10. 核心场景二：吃谷雷达

### 10.1 场景目标

吃谷雷达不是普通群发工具，而是商品事件决策系统。它根据虾淘 App / 小程序中的商品和活动变化，判断应该推给哪些群、什么时候推、用什么话术、是否需要人工审核、是否必须禁推。

### 10.2 商品事件类型

| 事件类型 | 示例 | 优先级 | 推送策略 |
|---|---|---|---|
| 新品开赏 | 蓝色监狱新池上线 | 高 | 匹配 IP 群和相关兴趣群 |
| 热门 IP 上新 | 原神新周边 | 高 | IP 兴趣群优先 |
| 隐藏款释放 | 稀有隐藏款重新进入奖池 | 极高 | 高价值群、高活跃群优先 |
| 补货 | 某角色吧唧补货 | 高 | 蹲谷用户和相关群优先 |
| 库存低位 | 剩余少量 | 中 | 仅高意向群提醒 |
| 限时活动 | 分享得激活码 | 中 | 根据群活跃和疲劳推 |
| 冷门清库 | 库存压力 | 低 | 默认需人工审核 |
| 履约风险商品 | 发货不稳定商品 | 禁止 | 不自动推送 |

### 10.3 商品事件字段

| 字段 | 说明 |
|---|---|
| event_id | 商品事件 ID |
| event_type | 新品、开赏、补货、隐藏款、库存低位等 |
| item_id | 商品 ID |
| ip_id / ip_name | IP 信息 |
| character_id / character_name | 角色信息 |
| category | 品类 |
| rarity_level | 稀有度 |
| price | 价格 |
| stock | 当前库存 |
| activity_id | 活动 ID |
| start_time / end_time | 活动时间 |
| mini_program_path | 小程序路径 |
| app_deep_link | App Deep Link |
| risk_flag | 履约风险、售后风险、禁推标记 |

### 10.4 推送决策逻辑

推送决策分为 9 步：

1. 接收商品事件；
2. 解析 IP、角色、品类、稀有度、库存和活动时间；
3. 查询群画像；
4. 过滤高风险群、禁推群、疲劳群；
5. 计算群匹配分；
6. 确定推送优先级；
7. 生成多版本文案；
8. 进入自动发送或人工审核；
9. 发送后回收点击、下单、负面和退群数据。

### 10.5 群匹配因子

| 因子 | 说明 |
|---|---|
| IP 匹配 | 群历史讨论或购买是否集中在该 IP |
| 角色匹配 | 群内是否频繁提到相关角色 |
| 品类匹配 | 群是否偏好吧唧、流麻、色纸等 |
| 活跃时间 | 当前是否是该群活跃时间段 |
| 转化历史 | 该群历史活动点击和下单表现 |
| 风险等级 | 高风险直接排除 |
| 疲劳度 | 推送过多则降频 |
| 库存压力 | 库存少则只推高匹配群 |
| 履约风险 | 有风险商品不自动推 |

### 10.6 推送内容模板

| 模板 | 使用场景 | 特点 |
|---|---|---|
| 新品开赏通知 | 新池上线 | 信息清晰，突出 IP 和开始时间 |
| 隐藏款提醒 | 稀有掉落 | 强调稀有度和限时性，但不夸大概率 |
| 补货提醒 | 用户蹲谷商品补货 | 强相关，适合高意向群 |
| 低库存提醒 | 库存紧张 | 谨慎使用，避免制造焦虑 |
| 新手友好说明 | 低门槛活动 | 附玩法解释 |
| 老玩家雷达 | 高价值群 | 语气更直接，少解释 |
| 群话题种草 | 高活跃低转化群 | 先互动再转化 |
| 活动倒计时 | 活动结束前 | 需控制频率 |
| 晒谷互动 | 活动后 | 鼓励分享体验 |
| 许愿收集 | 选品反馈 | 引导用户表达需求 |

### 10.7 小程序与 App 双承接

由于虾淘 App 用户接近 6 成，小程序用户占 3-4 成，吃谷雷达必须同时支持两种承接链路。

建议策略：

1. 群内卡片同时提供“小程序参与”和“App 打开”入口；
2. 已绑定 App 用户优先 App Deep Link；
3. 未识别 App 用户默认小程序；
4. App Deep Link 失败时降级到 H5 或小程序；
5. 所有链接必须带追踪参数；
6. 点击、加购、支付、退款都应回传归因。

### 10.8 频控与禁推规则

| 群状态 | 日营销推送上限 | 自动问答 | 互动话题 | 舆情监控 |
|---|---|---|---|---|
| 高活跃高转化 | 3-5 条 | 开启 | 开启 | 开启 |
| 普通群 | 1-3 条 | 开启 | 低频 | 开启 |
| 沉默群 | 0-1 条 | 开启 | 试探 | 开启 |
| 高疲劳群 | 0-1 条 | 开启 | 暂停 | 开启 |
| 售后风险群 | 0 条 | 开启 | 暂停 | 开启 |
| 维权风险群 | 0 条 | 谨慎 | 暂停 | 开启 |

禁推触发条件：

- 群风险等级达到 L2 以上；
- 过去 24 小时负面消息异常；
- 该群刚发生多人投诉；
- 客服任务未处理完成；
- 商品本身履约风险高；
- 运营手动设为禁推。

### 10.9 产研功能拆分

| 功能 | 一期 | 说明 |
|---|---|---|
| 商品事件接口 | 是 | 核心能力 |
| IP / 角色标签解析 | 是 | 可先用词典和规则 |
| 群匹配策略 | 是 | 首期群级为主 |
| 高风险群排除 | 是 | 必须做 |
| 图文卡片生成 | 是 | 首期模板化 |
| 小程序链接 | 是 | 必须支持 |
| App Deep Link | 视接口 | 架构预留 |
| 点击归因 | 是 | 必须做 |
| 订单归因 | 视接口 | 至少预留 |
| 个体私聊提醒 | 二期 | 首期先群级 |
| 自动 A/B | 二期 | 首期人工对照 |

### 10.10 验收标准

| 测试项 | 标准 |
|---|---|
| 商品事件识别 | IP、角色、品类、活动时间解析正确 |
| 群匹配 | 不向明显无关群大规模推送 |
| 高风险群排除 | L2 以上风险群不得收到营销推送 |
| 链接归因 | group_id、event_id、campaign_id 正确 |
| 频控 | 不超过群状态对应上限 |
| 推送后监测 | 能记录点击、负面、退群等反馈 |

## 11. 核心场景三：舆情监控与客诉治理

### 11.1 场景目标

舆情监控的目标不是替客服解释所有问题，而是在群体风险形成前识别、降温、分流和升级。

虾淘私域高危问题包括：不发货、退款困难、吞烫质疑、霸王条款、客服不回复、组织投诉、外部曝光等。

### 11.2 风险分级

| 等级 | 定义 | 示例 | 系统动作 |
|---|---|---|---|
| L0 正常 | 普通闲聊 / 轻微吐槽 | “等好久啊” | 记录即可 |
| L1 轻度不满 | 单人抱怨 | “怎么还没发货” | 可引导私聊 |
| L2 多人共鸣 | 多人接话 | “我也是”“都没发” | 预警运营，暂停营销 |
| L3 强烈投诉 | 出现退款、霸王条款、吞烫等 | “你们是不是吞烫” | 主管预警，群内安抚 |
| L4 群体维权 | 组织投诉 / 外部曝光 | “一起去黑猫/12315” | 公关 / 客服负责人升级 |
| L5 危机扩散 | 多群联动、外部传播 | 小红书、微博、投诉链接 | 应急机制 |

### 11.3 高危词体系

高危词库分为多类，不作为最终判断，只作为候选风险触发。

| 类别 | 示例 |
|---|---|
| 发货类 | 不发货、什么时候发、拖了多久、清关没动、预售太久 |
| 退款类 | 退款、退钱、不退、强制代币、余额、不到账 |
| 盲盒争议 | 吞烫、概率、暗改、隐藏款、抽不到、黑箱 |
| 规则质疑 | 霸王条款、不合理、欺负消费者、协议陷阱 |
| 客服失效 | 客服不回、没人管、踢皮球、敷衍 |
| 维权投诉 | 黑猫、12315、投诉、报警、起诉、维权群 |
| 外部曝光 | 小红书曝光、微博挂你们、发帖、截图 |
| 平台攻击 | 诈骗、跑路、割韭菜、店大欺客 |

### 11.4 关键词不是最终判断

系统不能只靠关键词决定风险等级。需要结合：

- 近 5 / 10 / 30 分钟负面消息数量；
- 负面发言人数；
- 是否出现“我也是”“+1”“同样没发”；
- 是否有人组织投诉；
- 是否有人发外部投诉平台链接；
- 是否存在历史高风险用户；
- 当前群是否刚被营销推送刺激；
- 相关商品是否确有履约风险；
- 客服任务是否超时未处理。

### 11.5 群体共振模型

单个用户抱怨通常是客服问题，多人接话则可能成为群体舆情。建议定义群体共振指标：

| 指标 | 说明 |
|---|---|
| negative_user_count_10m | 10 分钟内负面发言人数 |
| negative_message_count_10m | 10 分钟内负面消息数 |
| echo_keyword_count | “我也是”“+1”“同问”等共鸣词数量 |
| external_complaint_signal | 是否出现外部投诉平台 |
| organizer_signal | 是否出现组织维权话术 |
| marketing_triggered | 是否由刚才的营销推送引发 |
| unresolved_ticket_count | 相关未处理客服任务数 |

### 11.6 自动动作矩阵

| 风险等级 | 自动回复 | 转客服 | 禁推 | 主管预警 | 备注 |
|---|---|---|---|---|---|
| L0 | 否 | 否 | 否 | 否 | 仅记录 |
| L1 | 可轻度引导 | 可选 | 否 | 否 | 单人问题 |
| L2 | 标准安抚 | 是 | 12 小时 | 是 | 多人共鸣 |
| L3 | 标准安抚 | 是 | 24-72 小时 | 是 | 强投诉 |
| L4 | 极简安抚 | 是 | 是 | 紧急 | 维权风险 |
| L5 | 不自动多说 | 是 | 是 | 公关级 | 危机扩散 |

### 11.7 群内安抚话术边界

可以说：

- “大家的反馈我们已经看到。”
- “具体订单需要结合订单状态核实。”
- “群里不方便公开订单信息，建议先通过 1 对 1 客服处理。”
- “我们会把这类问题同步给运营同学重点跟进。”

不能说：

- “大家别刷屏。”
- “这是正常情况。”
- “我们没有问题。”
- “规则就是这样。”
- “一定马上发。”
- “你去找客服。”
- “你误会了。”

### 11.8 不发货客诉专项治理

#### 风险类型

| 类型 | 示例 | 处理方式 |
|---|---|---|
| 单人催发货 | “我的怎么还不发” | 私聊查询 |
| 多人共鸣 | “我也是”“都多久了” | 群内安抚 + 多人私聊 |
| 规则质疑 | “霸王条款”“退款不合理” | 主管预警 |
| 平台指控 | “吞烫”“诈骗” | 红色预警 |
| 外部投诉 | “黑猫/12315/小红书曝光” | 公关升级 |

#### 标准处理流程

1. 识别发货类负面；
2. 判断单人还是多人；
3. 若单人，触发私聊客服；
4. 若多人，群内先极简安抚；
5. 自动禁推营销；
6. 创建客服任务包；
7. 通知运营主管；
8. 客服处理后回写；
9. 系统判断是否解除风险。

### 11.9 与客服 Agent 联动

私域 Agent 向客服 Agent 传递：

- 用户 ID；
- 群 ID；
- 风险等级；
- 触发消息摘要；
- 可能关联订单；
- 用户情绪；
- 建议优先级；
- 是否多人共振；
- 群是否已禁推。

客服 Agent 回写：

- 工单状态；
- 是否已接待；
- 是否已处理；
- 处理结论摘要；
- 是否可解除风险；
- 是否需要主管继续跟进。

### 11.10 验收标准

| 测试项 | 标准 |
|---|---|
| 高危词触发 | 不发货、退款、吞烫、霸王条款可触发候选风险 |
| 上下文判断 | 玩梗与真实投诉可区分到可接受水平 |
| 多人共振识别 | 多人接话可提升风险等级 |
| 禁推机制 | 风险群自动暂停营销 |
| 客服联动 | 可生成客服任务并回写状态 |
| 主管预警 | L3 以上必须触达主管 |
| 安抚边界 | 不承诺、不争辩、不公开处理订单 |

## 12. 群内互动与销量提升策略

### 12.1 互动的作用边界

群互动不是为了让 Agent 陪聊，而是服务于四个运营目标：

1. 提升群活跃；
2. 提升新品 / 活动点击；
3. 收集 IP / 角色需求；
4. 降低纯营销打扰感。

### 12.2 可落地互动场景

#### 场景 A：蹲谷日历

用户说“蹲蓝锁补货”“蹲凪吧唧”“这个再贩踢我”时，Agent 记录为蹲谷意向。补货或上新时，优先提醒相关群或用户。

一期以群级提醒为主，二期再做个人私聊提醒。

#### 场景 B：欧气播报

用户晒中隐藏款 / 大赏时，Agent 轻度互动，营造抽赏氛围。

要求：

- 不夸大中奖概率；
- 不暗示继续抽一定会中；
- 不制造过度消费压力；
- 只做情绪氛围，不做诱导性承诺。

#### 场景 C：角色许愿榜

每周生成：

- 本群许愿最多 IP；
- 本群许愿最多角色；
- 本群最想补货品类；
- 本周群内热度变化。

用途：

- 提升群参与；
- 反哺选品；
- 反哺吃谷雷达推送。

#### 场景 D：新手入坑路线

对新手群或新手用户较多的群，Agent 可以低频发布：

- 什么是抽赏；
- 如何看奖池；
- 什么是出荷；
- 预售和现货区别；
- 如何避免错过补货；
- 新手适合关注哪些低门槛活动。

#### 场景 E：老玩家专属雷达

对老玩家和高价值群，减少基础科普，重点推：

- 稀有款；
- 补货；
- 隐藏款释放；
- 同角色新品；
- 同 IP 限时活动。

### 12.3 互动频控

| 群类型 | 互动频率 | 说明 |
|---|---|---|
| 高活跃高转化群 | 每日 1-2 次 | 可围绕新品和晒谷 |
| 高活跃低转化群 | 每日 1 次 | 以话题和许愿为主 |
| 低活跃群 | 每周 2-3 次 | 测试唤醒，不刷屏 |
| 高风险群 | 暂停互动 | 只做服务和安抚 |
| 投诉恢复期群 | 暂停营销型互动 | 避免刺激用户 |

## 13. Agent 编排架构

### 13.1 不使用单一总 Agent

生产环境不应让一个大模型承担所有任务。建议拆成多个职责明确的 Agent，由编排层调度。

### 13.2 Agent 列表

| Agent | 主要职责 | 不负责 |
|---|---|---|
| 消息理解 Agent | 意图分类、IP/角色提取、情绪初判 | 不直接回复 |
| 谷子问答 Agent | 术语、玩法、活动规则回答 | 不处理订单纠纷 |
| 商品事件 Agent | 解析新品、开赏、补货、隐藏款事件 | 不做支付和抽奖逻辑 |
| 群运营策略 Agent | 判断群能否推、推什么、何时推 | 不绕过频控 |
| 舆情监控 Agent | 风险识别、分级、禁推、预警 | 不和用户争辩 |
| 客服协同 Agent | 生成客服摘要、创建任务、接收回写 | 不直接判责 |
| 运营复盘 Agent | 日报、周报、群/IP/活动复盘 | 不自动改变核心策略 |
| Guardrail Agent | 审核所有外发内容 | 不生成业务主内容 |

### 13.3 编排原则

1. 先识别，再决策，再生成，再审核，再执行。
2. 每个 Agent 的输入输出必须结构化。
3. 所有外发内容必须经过 Guardrail。
4. 高风险场景优先转人工，不追求自动闭环。
5. 任何 Agent 失败都应降级为“不回复 / 转人工 / 运营审核”。

### 13.4 典型调用链路

#### 术语问答链路

群消息 -> 消息理解 Agent -> 谷子问答 Agent -> Guardrail Agent -> 群回复 -> 日志写入。

#### 吃谷雷达链路

商品事件 -> 商品事件 Agent -> 群运营策略 Agent -> 文案生成 -> Guardrail Agent -> 发送 / 审核 -> 点击回传 -> 复盘 Agent。

#### 客诉风险链路

群消息 -> 消息理解 Agent -> 舆情监控 Agent -> 禁推 -> 安抚话术生成 -> Guardrail Agent -> 客服协同 Agent -> 主管预警 -> 状态回写。

## 14. 模型选型与调用策略

### 14.1 模型调用分层

| 层级 | 用途 | 技术建议 |
|---|---|---|
| L0 规则层 | 高危词、术语词、IP词、角色词快筛 | 正则、AC 自动机、词典匹配 |
| L1 轻量分类层 | 消息意图、情绪倾向 | 小模型分类器或轻量 LLM |
| L2 RAG 问答层 | 谷子词典、活动规则问答 | Qwen / DeepSeek + RAG |
| L3 深度判断层 | 舆情上下文、多轮投诉、复杂意图 | 更强模型 |
| L4 内容生成层 | 推送文案、日报总结 | 中等成本生成模型 |
| L5 审核层 | 群发内容安全审查 | 规则 + 强模型复核 |

### 14.2 推荐模型组合

| 任务 | 推荐方案 | 原因 |
|---|---|---|
| 术语识别 | 词典 / 规则 | 成本低、稳定 |
| IP / 角色识别 | 词典 + Embedding | 支持别名、昵称、错别字 |
| 意图分类 | 小模型 / 分类器 | 万群消息成本可控 |
| 谷子问答 | Qwen2.5 / Qwen3 / DeepSeek Chat + RAG | 中文能力和成本平衡 |
| 舆情判断 | DeepSeek V3 / Qwen Max 类能力 | 需要上下文和情绪判断 |
| 推送文案 | Qwen / DeepSeek | 成本可控、风格可控 |
| 长报表总结 | 长上下文模型 | 适合日报周报 |
| 向量检索 | BGE-m3 / Qwen Embedding | 中文和混合语义较好 |
| 重排序 | bge-reranker / 同类 reranker | 提高 RAG 准确率 |

### 14.3 成本控制规则

1. 群内普通闲聊不进入大模型。
2. 未命中高危词、术语词、商品词的消息默认只做轻量统计。
3. 只有被 @、触发关键词或满足风险窗口时才进入 LLM 链路。
4. 同群同问题启用冷却。
5. 同一商品事件的文案生成可缓存复用。
6. 舆情复核只对候选风险进行，不全量跑。

## 15. 记忆系统与上下文管理

### 15.1 记忆系统原则

1. 不保存无价值闲聊原文；
2. 优先保存结构化标签，而不是完整聊天；
3. 高风险证据短期保留，并设置权限；
4. 用户免打扰、退群、拒绝触达必须被写入长期状态；
5. 记忆写入必须有来源、时间、置信度和过期策略。

### 15.2 记忆类型

| 记忆类型 | 内容 | 保存方式 | 用途 |
|---|---|---|---|
| 群短期记忆 | 最近 10-30 分钟上下文 | Redis / 短期表 | 判断刷屏、共振、重复问答 |
| 群长期画像 | IP、活跃、转化、风险、疲劳 | PostgreSQL | 群运营策略 |
| 用户长期画像 | IP 偏好、角色偏好、蹲谷、风险 | PostgreSQL | 用户级运营 |
| 商品事件记忆 | 推送过哪些群、效果如何 | PostgreSQL | 推送优化 |
| 知识记忆 | 术语、规则、SOP、活动说明 | 向量库 + 文档库 | RAG 问答 |
| 舆情证据 | 风险摘要、关键发言、状态 | 受限权限表 | 客服和主管处理 |

### 15.3 上下文组装

不同任务加载不同上下文，避免把无关信息塞给模型。

| 任务 | 加载上下文 |
|---|---|
| 术语问答 | 用户问题、命中知识片段、群冷却状态 |
| 活动规则 | 当前活动版本、用户问题、禁止承诺规则 |
| 吃谷推送 | 商品事件、群标签、群风险、频控状态 |
| 舆情判断 | 最近窗口消息、群风险、用户历史、客服状态 |
| 安抚话术 | 风险摘要、禁止承诺规则、客服入口 |
| 日报总结 | 当日事件、推送结果、风险记录、未命中问题 |

### 15.4 上下文压缩

| 原始信息 | 压缩结果 |
|---|---|
| 多条群聊原文 | 群事件摘要 |
| 多人投诉 | 群体风险摘要 |

### 15.5 OpenViking 类记忆选型

## 16. System Prompt 与 Guardrail 设计

### 16.1 总控原则

所有 Prompt 必须遵守：

1. 业务边界优先于表达风格；
2. 不确定则不回答或转人工；
3. 高风险不营销；
4. 群内不处理订单隐私；
5. 不承诺发货、退款、补偿；
6. 不争辩；
7. 所有外发内容进入 Guardrail。

### 16.2 群运营策略 Agent Prompt

角色：你是虾淘私域群运营策略 Agent，负责判断某个群在当前状态下是否适合推送、适合推送什么、是否需要人工审核。

输入：

- 群画像；
- 群风险等级；
- 群疲劳度；
- 商品事件；
- 活动优先级；
- 过去 24 小时推送记录；
- 过去 24 小时负面记录。

判断规则：

1. 如果群风险等级为 L2 及以上，禁止营销推送。
2. 如果群疲劳度为高，降频或不推。
3. 如果商品 IP 与群 IP 不匹配，不推或低优先级。
4. 如果商品履约风险高，不自动推。
5. 如果库存低但群匹配低，不推。
6. 如果群高转化且匹配高，可以优先推。
7. 如果需要人工审核，输出原因。

输出：

- 是否推送；
- 推送优先级；
- 目标群；
- 推荐模板；
- 是否需要审核；
- 不推原因；
- 预估风险。

### 16.3 舆情监控 Agent Prompt

角色：你是虾淘群内舆情监控 Agent，负责判断群内消息是否存在售后、退款、不发货、吞烫、维权等风险，并给出风险等级和处理动作。

规则：

1. 不以单个关键词直接判定高风险，必须结合上下文。
2. 多人共鸣比单人抱怨风险更高。
3. 出现外部投诉、组织维权、平台诈骗指控时必须升级。
4. 判断风险后不输出营销内容。
5. 只输出结构化结果，不直接面向用户说话。

输出字段：

- risk_level；
- risk_type；
- involved_users；
- evidence_summary；
- need_disable_marketing；
- need_customer_service；
- need_supervisor_alert；
- suggested_group_reply；
- confidence。

### 16.4 Response Guard Prompt

角色：你是虾淘群消息安全审核 Agent，负责审核所有即将发送到群内的内容。

必须拦截：

- 承诺具体发货时间；
- 承诺退款结果；
- 承诺补偿；
- 公开索要订单号；
- 责怪用户；
- 与用户争辩；
- 在风险群营销；
- 夸大中奖概率；
- 制造过度消费焦虑；
- 违反活动规则；
- 与当前知识库版本冲突。

输出：

- pass / reject / revise；
- 拦截原因；
- 修改建议；
- 安全版文案。

## 25. 最终产研结论

虾淘私域运营 Agent 的核心不是“让 AI 在群里聊天”，而是建立一套群资产运营系统。

一期最应该解决三个问题：

1. **群能不能被识别和分层**  
   先知道哪些群高价值、哪些群疲劳、哪些群高风险、哪些群适合某个 IP。

2. **活动能不能被精准且安全地推送**  
   新品、补货、隐藏款不是简单群发，而是基于群画像、风险等级和频控触发。

3. **客诉能不能被提前发现和阻断**  
   不发货、退款、吞烫、霸王条款等信号必须在群体化前识别，并自动禁推、转客服、预警主管。

因此下一步产研应按以下顺序推进：

1. 企微权限与接口确认；
2. 群资产模型落地；
3. 三大核心场景 MVP；
4. Guardrail 和禁推机制；
5. 后台与复盘闭环；
6. 试点群灰度；
7. 根据数据扩展到用户级精细运营。

只要系统坚持“群级优先、风险优先、数据闭环优先、模型分层调用、人工可接管”，这套 Agent 才能从 demo 变成真实生产环境中可持续运行的私域运营系统。
