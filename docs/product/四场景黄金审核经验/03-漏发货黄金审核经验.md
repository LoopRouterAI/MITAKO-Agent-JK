## 1. 有效结论摘要

1. 人工审核先建立受信的“应发事实”，再确认全部物流和包裹边界，随后选择用户证据路线，最后做应发/实收对账；不能从用户一句“漏发了”或订单截图直接跳到结论。
2. 应发清单只来自系统订单行、SKU、规格、数量和版本化活动规则。商品标题、系列名、宣传组合图、“特典”等文字不自动增加独立应发项。
3. 合规开箱视频是可直接做视觉对账的首选路线。同一视频证据链必须同时满足：封箱起始、视频内面单可读、面单匹配当前订单、一镜到底、开箱完成、全部内容可清点。
4. 无合规视频时，全部到手实物全家福、绿色自封袋、清晰且匹配订单的面单三类静态材料全部合格，只表示用户侧材料齐全；必须转人工客服读取仓库实发明细，Agent 不得自行确认漏发，也不得直接拒绝。
5. `evidence_route`（用户证据路线）与 `resolution_basis`（最终事实依据）必须分轴。材料齐全不等于诉求成立，仓库终核也不能伪装成视觉观察。
6. Gemini 只提取可见原子事实和证据引用；程序持有受信业务基线，完成分包归属、数量归并、差集计算、冲突处理与确定性 SOP 决策。
7. 若实收中出现未购商品且应收商品缺失，应切换或并列发错货语义；只有“少了应收项”才保留漏发语义。
8. 纸类叠放、背面和夹层检查只在确认漏发后作为用户自查提醒，不能成为前置门槛，也不能由模型凭单帧推断已检查或未检查。

## 2. 人工客服的真实审核顺序

### 2.1 先拆诉求，不先判结论

- 将用户描述拆成一个或多个原子主张：缺少哪个 SKU、规格、款式、部件或数量。
- 用户没有点名具体 SKU 时，先尝试将完整应发清单与完整实收集合逐项排除；追问具体 SKU 只是提效动作，不是拒绝审核的理由。
- 若同一工单同时包含漏发、有伤或其他诉求，各原子诉求独立审核，不能用其中一个结论覆盖另一个。

### 2.2 建立应发清单

依次读取系统订单行、SKU、规格、数量、商品主数据、版本化活动/赠品/随机款规则。每个应发项至少保留：

```text
expected_item:
  order_line_id
  sku
  specification
  expected_quantity
  obligation_type: purchased | bundled_component | promotion_gift
  rule_version
  rule_source
```

用户订单截图只作辅助展示，不能替代系统事实。若商品构成或活动规则尚未有受信版本，相关应发项必须保持待确认，不能从标题拆词补全。

### 2.3 核对包裹、分包与物流

- 读取订单下全部物流单、包裹映射、签收状态和分批发货状态，不只看用户当前展示的一张面单。
- 将每个应发项映射到目标包裹；存在多物流或分包时，先核完全部相关包裹再计算缺项。
- 另拍的面单照片不能自动绑定到另一段开箱视频中的箱体；视频必须在同一连续证据链内展示当前订单面单。
- 未签收、在途、物流异常或包裹缺失属于物流/履约待核，不应伪装成仓库已确认漏装。

### 2.4 选择证据路线

```text
evidence_route:
  compliant_opening_video
  static_three_images
  insufficient
  not_required
```

- 有候选视频：逐项审核合规六要素，不因文件名叫“开箱视频”就视为合格。
- 无合规视频：检查静态三图是否全部齐全、清晰、同包裹、可清点。
- 商品主数据已证明用户主张项不属于应发义务时，路线为 `not_required`，不得伪称“用户材料齐全”。
- 两条用户证据路线都未闭环时，精准列出缺项并补件，不用模糊的“资料不足”结束。

### 2.5 形成实收清单并对账

合规视频路线下，人工从同一包裹连续开箱链中建立逐包裹实收清单；静态路线下，Agent 只建立可见清单并标记其证据层级，不能把平铺图当成包裹原始实收事实。程序随后按 `包裹 + SKU/构成身份 + 数量` 归并，并计算：

```text
missing_quantity = expected_quantity - received_quantity
```

差值大于零且证据闭环，才形成漏发事实倾向。若身份或数量看不清，输出 `unknown`，不得将“未识别到”写成“未收到”。

### 2.6 根据事实依据落结论

```text
resolution_basis:
  visual_reconciliation
  warehouse_verification
  trusted_expected_item_resolution
  none
```

- 合规视频完整对账：可以 `visual_reconciliation` 形成漏发或未发现漏发的视觉事实倾向。
- 静态三图齐全：只能进入 `warehouse_pending`，等待仓库终核。
- 商品构成消歧：受信商品主数据可以证明主张项不属于应发义务，但 568689 类争议当前仍需保留仓库终核边界。
- 证据不闭环：`resolution_basis=none`，给出唯一可执行下一步。

## 3. 必需输入与材料齐全性

### 3.1 程序盘点必须输入

| 输入组 | 必需内容 | 缺失时处理 |
|---|---|---|
| 用户诉求 | 原始诉求、原子缺项、数量；未点名时允许全量排除 | 可追问具体 SKU 提效，不直接拒绝 |
| 应发基线 | 系统订单行、SKU、规格、数量、基线版本和来源 | 无法计算漏发，保持待确认 |
| 商品规则 | 构成、附件、赠品、特典、随机/隐藏/选择规则及版本 | 不从标题或宣传图推断 |
| 履约事实 | 全部包裹、全部物流、应发项到包裹映射、签收状态 | 先核分包/在途，不做整单差集 |
| 用户证据 | 全部图片、视频及素材哈希、去重关系、可解码状态 | 技术失败单列系统错误，不算用户缺件 |
| 仓库事实 | 可用状态、受信来源、核验编号、核验时间、逐包裹实发清单 | 未提供时只能 `not_available/pending` |

### 3.2 合规视频路线的材料齐全

六项全部为可证实的 `true` 才视为 `compliant_opening_video`：

1. 从未拆封/封箱状态开始。
2. 视频内清晰展示快递面单。
3. 面单可与当前订单及目标包裹匹配。
4. 关键开箱过程一镜到底，未被破坏性剪辑或断点打断。
5. 快递箱及内包装完成拆开。
6. 箱内全部商品与数量都被清晰展示，可建立实收清单。

其中任一项为 `false/unknown`，视频路线不完整。存在视频不等于视频合规；仅有关键帧也不能证明连续性。

### 3.3 静态三图路线的材料齐全

三类材料缺一不可：

1. 全部到手实物全家福，主体和数量可清点。
2. 该包裹的绿色自封袋/包装袋，来源关系可辨。
3. 清晰快递面单，且能匹配当前订单与目标包裹。

三项齐全时：`material_readiness=complete`、`evidence_route=static_three_images`、`warehouse_check.state=pending`。这三个状态必须同时展示，禁止将 `complete` 翻译成“已确认漏发”。

## 4. 商品构成、赠品与分包规则

### 4.1 商品构成消歧

按以下优先级确定应发义务：系统独立订单行/SKU > 受信商品构成 > 版本化活动规则 > 标题与宣传展示。标题与宣传展示只能帮助定位规则，不能单独创建应发项。

- 系列标题带“特典”，不代表另有一件独立特典。
- 同一系列同时售卖本体和圆卡，不代表购买本体会附赠整套圆卡。
- 宣传图呈现组合效果，不代表每个画面元素都是所购 SKU 的独立部件。
- “套装拆卖”“单配”“随机一张”等规则必须按具体 SKU 和规则版本解释，不能借用订单中其他商品的规则。

若商品构成已证明争议项从未属于应发义务，应把该主张从差集计算中移除，并给出可读解释；不能把它记成“实收数量为零的漏发项”。

### 4.2 赠品、特典和随机规则

- 赠品只有在版本化活动规则明确命中订单条件时才进入应发清单。
- 规则须记录活动标识、适用时间、门槛、数量、选择/随机机制和来源。
- 随机款表示款式差异被规则允许，不代表数量缺失被允许。
- 端盒保配、拆袋确认款式、单配等规则必须落到用户实际购买方式，不能按系列通用描述推断。
- 无可信规则时标记 `unknown` 并转业务核验，不判漏发，也不判“规则不包含”。

### 4.3 分包、多物流和分仓

- `splitShipment=true` 时，差集必须按全部相关包裹汇总，而不是对单包裹直接判整单漏发。
- 未签收或仍在途包裹中的应发项不能计入当前包裹漏发。
- 仓库回传“拆包/分仓”只是解释履约路径；仍需核对每个包裹的物流和最终实发数量。
- 包裹映射未知时保持 `unknown`，不可根据箱体大小、商品相似度或用户拍摄顺序猜归属。

## 5. 仓库终核字段

```text
warehouse_check:
  state: not_available | pending | verified
  outcome: confirmed_missing | confirmed_not_missing | split_or_warehouse | rule_not_included | null
  baseline_version
  source_system
  verification_id
  verified_at
  packages[]:
    package_id
    logistics_ref
    shipped_items[]:
      sku
      specification
      shipped_quantity
```

终核必须能够追溯到受信仓库记录。没有来源、编号、时间和逐包裹实发明细时，只能写 `not_available/pending`；不能因为客服口头倾向、最终补发或拒绝动作而补写仓库事实。仓库终核覆盖早期视觉疑似结论时，程序必须清理旧的差集、旧结论理由和旧下一步，避免报告同时出现“疑似漏发”和“确认未漏装”。

仓库记录的完整度只描述可追溯性，不等于事实准确率，也不得硬编码为 `1.0` 置信度。

## 6. Gemini 原子事实与程序对账

### 6.1 Gemini 只输出观察事实

每项事实使用 `true | false | null` 或明确枚举，并携带 `confidence`、自然语言理由和真实 `evidence_refs`：

```text
opening_video_facts:
  sealed_start
  waybill_visible
  waybill_text_observed
  continuous_opening
  opening_completed
  all_contents_visible
  observed_packages[]
  received_items[]:
    observed_identity
    observed_quantity
    package_ref
    evidence_refs[]

static_facts:
  full_received_group_visible
  green_bag_visible
  waybill_visible
  waybill_text_observed
  received_items[]
```

模型不得输出或猜测：系统应发清单、活动适用性、分包归属、仓库是否漏装、退款/补发/拒绝、责任归属。用户声称、文件名、目录名和黄金标签均不是视觉事实。

### 6.2 程序负责确定性对账

程序执行顺序固定为：

1. 校验素材可读性、哈希和重复关系。
2. 读取受信应发清单、商品规则、全部包裹和物流。
3. 用模型事实判定证据路线和材料齐全性。
4. 仅在同包裹、身份可比、数量可数时归并实收项。
5. 对每个包裹计算应发/实收差集，并保留 `unknown` 和冲突。
6. 应用仓库终核覆盖规则。
7. 生成唯一结论、唯一下一步和两层报告。

同一素材只能聚合一次；后续仓库事实是独立来源，不反向改写模型观察。对账程序不得把低置信“未检测到”当成数量 `0`。

## 7. 与发错货场景的切换

| 对账结果 | 场景语义 |
|---|---|
| 应收项缺失，未发现额外未购商品 | 漏发货 |
| 出现未购商品，同时应收商品缺失 | 发错货为主，可保留漏发原子差异 |
| 商品身份属性冲突，但数量没有缺失 | 发错货 |
| 仅页面尺寸、拍摄角度、普通描述差异 | 不足以判发错或漏发，保持待确认 |
| 包裹关系、随机规则或商品构成未知 | 不切换成确定场景，先补受信事实 |

切换场景时保留原始用户诉求和已经建立的包裹证据，但重新使用发错货的身份属性 Schema、材料清单、决策和报告视图；不能在漏发报告模板里硬写“发错”。

## 8. 报告双层结构

### 8.1 首层：客服可直接行动

首层固定回答：

1. 漏发事实倾向与证据确定性。
2. 用户材料是否齐全。
3. 当前 `evidence_route` 与 `warehouse_check.state`。
4. 唯一下一步：补哪项材料、转仓库核验、继续程序对账，或在证据闭环后进入人工终审。

示例表达原则：静态三图齐全时应写“用户侧材料齐全，待核仓库实发”，不能写“确认漏发”；合规视频缺面单时应写“当前包裹与订单未关联，补视频内面单或走静态三图路线”。

### 8.2 第二层：可审计事实

详情展示：

- 应发清单及基线版本。
- 逐包裹物流、签收、分包映射。
- 合规视频六项，或静态三图三项及面单匹配。
- 逐包裹实收商品、数量和证据引用。
- 商品构成、赠品/特典/随机规则。
- 程序差集、冲突与未知项。
- 仓库核验来源、编号、时间和逐包裹事实。
- 纸类提醒（仅在适用且确认漏发后显示）。

公开报告不展示个人字段原值、完整运单号、内部路径、模型渠道、Key、Prompt、原始 JSON、黄金标签或人工答案。内部枚举需翻译成业务语言，证据引用需回链原素材或可信系统记录。

## 9. 禁止推断与失败保护

- 禁止从用户陈述生成实收清单，或从最终补发/赔付/拒绝倒推初始事实。
- 禁止把仓库结论写成视频/图片观察，也禁止用视觉结果伪造仓库核验。
- 禁止把另拍面单绑定到未展示面单的视频箱体。
- 禁止把空袋、局部短视频、播放器截图或关键帧当作完整连续开箱。
- 禁止把商品标题、系列名、宣传组合或“特典”字样拆成额外应发项。
- 禁止忽略第二包裹、在途包裹、分仓或多物流后直接判漏发。
- 禁止把未点名 SKU 本身写成证据不足；只有无法完成全量排除时才补问。
- 禁止把“模型没看见”写成“商品不存在”；不可辨识使用 `unknown`。
- 禁止把静态三图齐全写成诉求成立，或无视频直接写成拒绝。
- 禁止将纸类夹层提醒作为确认漏发的前置条件。
- 禁止以少量黄金 Case 声明准确率、生产最优或人工节省比例。
- 技术解析失败必须单列 `system_error` 并重试/转人工，不能伪装成用户缺材料。

## 11. 待甲方确认

1. 可信商品主数据能否在所有 568689 类商品构成争议中独立形成终态，还是仍必须仓库终核。当前按更保守口径：商品构成可形成不属于应发义务的事实，但该类关闭规则待甲方明确。
2. 合规完整视频对账在所有品类能否直接形成最终事实，还是某些高风险品类仍需仓库终核。
3. 绿色自封袋的正式识别定义、允许替代包装及“一包多个、无法单独保留原袋”等例外的版本化适用范围。
4. 分仓/拆包、赠品、随机款、端盒保配和拆袋确认款式规则由哪个甲方系统提供，字段、版本号和失效机制如何定义。
5. 仓库终核接口的真实字段、核验编号、来源系统、时间和逐包裹实发明细尚未接入；当前只能保留 Mock/契约说明，不得声称已经在线核验。
6. 静态三图中“全部实物全家福”的数量可读门槛，以及多层叠放、透明袋反光、同款多件时的补拍标准。
7. 纸类自查提醒适用品类的正式清单，以及用户确认找到夹层商品后如何回写并撤销旧漏发结论。

## 12. 开发与验收入口

实现时应保持一条主链：`review_inventory -> Gemini 原子事实 -> material_readiness/evidence_route -> 程序对账 -> warehouse_check -> 确定性决策 -> 漏发货双层报告`。不得新建平行的“案例关键词判定器”，也不得把 Case ID、黄金结论、人工备注或目录标签送入模型。

最小验收集合应覆盖：标准确认漏发、视频缺面单、视频未展示全部内容、静态三图缺项、静态三图齐全待仓库、仓库确认未漏装、商品构成误解、未点名 SKU、分包未核完、发错语义切换和纸类提醒时序。正式盲验必须使用未泄题材料，并分别验证 JSON 与报告同源、证据可回看、公开脱敏和唯一下一步；不得以本指南中的已学习 Case 编造准确率。
