## 1. 文档定位与证据优先级

本文把人工黄金经验转成 Prompt、Schema、材料门禁、确定性策略和报告视图可直接消费的规则。所有结论只针对当前审核时点已经收到且可读取的资料；最终换货、退款、补偿、仓库后续答复不能倒推初始材料充分。

发生冲突时按以下顺序处理：

1. 甲方客服主管最新明确确认。
2. 人工终审表/黄金标。
3. 当前正式 SOP 与 2026-08-13 定稿 HTML 指南。
4. 可泛化案例经验。
5. 历史实现、旧报告和售后结果。

但后发资料只覆盖其明确冲突的旧字段，不能整案吞并。当前综合契约已明确：`56790` 样本过旧且本地删除，不参与业务学习、盲验或完成度统计；HTML 中保留的历史记录只能作为“静态差异不等于同包裹实收”的反面说明，不能作为验收 Case。

本轮只读核对了客户核对表中全部发错货相关行：共覆盖 25 个案例、67 个分歧字段，主管最终值均已填写。字段主要包括初始错发事实、应发 SKU 核对、应发/实收差异、官方图比对、随机规则、仓库事实和最终动作。表内仍存在少量字段间或与定稿 HTML 的冲突，本文不把冲突值静默归一。

## 2. 人工客服真实审核顺序

人工审核不是先看用户说“发错了”，也不是先看最终是否换货，而是按证据链逐层收窄：

```text
拆分用户主张并确认发错货场景
  -> 盘点当前轮全部订单、规则、物流和媒体
  -> 建立版本化应收基线
  -> 建立当前订单包裹归属
  -> 判断开箱视频链或静态降级链是否成立
  -> 识别完整实收集合及商品身份属性
  -> 逐项计算应收与实收差异
  -> 应用随机/隐藏/特典/版本规则
  -> 判断是否切换漏发或商品信息场景
  -> 必要时读取可追溯仓库事实
  -> 输出事实结论、材料状态和唯一下一步
```

执行细节：

- 先核订单具体 SKU、款式、版本和数量。未建立应收基线时，不得直接判断错发。
- 再核包裹归属。商品照片“看起来不是订单商品”不证明它来自当前订单包裹。
- 再核全部实收。多 SKU 订单不能只看争议单品或总件数；要识别“缺了谁、多了谁、是否重复替代”。
- 最后才判差异性质。商品身份不变但尺寸、普通描述或拍摄角度不同，不属于发错；只缺应收而没有错误商品，切换漏发。
- 仓库事实与媒体事实分别记录。没有可追溯记录时，仓库状态只能是“无仓库结论”或“待核验”。
- 最终经营动作单独记录。换货、退款、补偿或拒绝不是媒体事实，也不应由视觉模型决定。

## 3. 必需输入与程序盘点

### 3.1 受信业务输入

发错货审核至少需要：

- 用户原始主张及争议项，不把客服转述自动当事实。
- 版本化订单行：订单版本、SKU、名称、角色/款式、系列、版本、形态、附件构成、数量。
- 包裹与物流映射：分包关系、受信运单标识、订单与包裹的对应关系。
- 版本化活动规则：随机款、隐藏款、拆袋确认款、特典、国版/日版、端盒或配件规则。
- 官方商品图或受信商品主数据；只用于建立应收基线，不能代替实收证据。
- 用户媒体及来源关系：原视频、图片、面单、全部实收、包装/绿色自封袋标签。
- 如需终核：带来源、时间和可追溯标识的仓库实际打包记录或权威核实结果。

任何关键业务输入缺失时应显式为 `unknown/null`，不能让 Gemini 从商品外观、文件名、用户文案或历史售后动作中猜出订单、运单、SKU 或仓库事实。

### 3.2 程序盘点字段

进入模型前，程序生成 `review_inventory`：资产标识、脱敏文件名、来源、媒体类型、受信 MIME、哈希、去重关系、图片尺寸、视频时长/编码/可解码状态，以及订单、商品主数据、官方图、物流、活动规则、仓库快照是否存在。技术失败单列 `system_error`，不得伪装成用户未提交材料。

## 4. 材料齐全性与同包裹闭环

`material_readiness` 只回答“现有资料是否足以执行当前审核路径”，不等于确认错发，也不等于应换货。

### 4.1 视频主路径

完整视频链至少核验：

1. 从完整未拆包裹开始。
2. 开箱过程连续，目标包裹及内容物可持续追踪。
3. 视频内存在清晰面单或可与目标箱体连续绑定的唯一内包面单。
4. 面单与受信订单物流逐项匹配。
5. 展示全部到手商品，身份和数量可识别。
6. 需要时展示包装/绿色自封袋及可核验标签。

不能机械套字段：

- 同画面出现多个邮包不自动破坏证据链；目标箱体在完整视频中可连续追踪即可。
- 外箱面单未入镜时，仅在“封箱外箱连续拆出唯一内包、内包始终可追踪、内包面单清晰且匹配订单”等严格限定条件下，可由唯一内包面单完成关联。
- 单 SKU、唯一未拆密封袋、连续拆出唯一商品可在限定条件下合理接受开箱起点；多 SKU、多袋、袋体已拆或视频不连续时禁止泛化。
- 静态面单不能自动绑定到另一个缺少面单的视频箱体；必须有同物、同包裹的连续关联证据。
- 关键帧只负责证据定位，连续性、离框和覆盖范围必须按完整视频判断。

### 4.2 静态降级路径

无合规开箱视频时，静态链至少包括：

- 全部到手实物全家福平铺图，商品身份与数量可核对。
- 包装/绿色自封袋及清晰标签。
- 清晰面单且与订单物流匹配。

三类静态材料齐全，只表示达到人工/仓库核验入口。对当前资料体系，图片本身通常不能证明仓库当时实际装箱内容；需读取可追溯仓库记录后再形成仓库终态。若只有争议商品特写、页面截图、缺少完整实收、缺标签或缺当前包裹关联，应判 `incomplete/indeterminate` 并点名补件。

### 4.3 材料状态建议

```text
complete:
  当前选定审核路径的必需项全部存在、有效、可回链

incomplete:
  已明确缺少某一必需项，例如无匹配面单、未展示全部实收

indeterminate:
  文件已提供但不可读、主体不可识别、同包裹关联或规则适用性无法判断

not_required:
  受信规则已证明某材料在本案不适用；必须记录理由，不能为了凑齐而使用
```

## 5. 应收与实收：身份属性优先

### 5.1 应收基线

应收只能由受信订单、商品主数据和版本化活动规则生成。应收项至少包含：

```text
expected_items[]:
  order_line_ref, sku_ref, package_ref
  item_role, series, edition, physical_form
  included_parts[], quantity_expected
  rule_version, reference_image_refs[]
```

不能只按基础 SKU 名称判断。即使基础 SKU 相同，本次售卖明确承诺的角色、版本、圆角/方角等形态或必要附件不同，仍可能是错误交付。

### 5.2 Gemini 原子事实

Gemini 只提取画面可见内容，不做应收推断和经营裁决：

```text
observed_items[]:
  subject_ref, package_ref
  item_role, series, edition, physical_form
  included_parts[], visible_identifiers[]
  descriptive_dimensions[]
  quantity_observed
  confidence, evidence_refs[]

package_observations[]:
  package_ref
  sealed_start, continuous, waybill_visible
  waybill_observed, all_items_shown
  package_or_bag_label_visible
  confidence, evidence_refs[]
```

每个字段必须独立给 `confidence/reason/evidence_refs`；看不清写 `unknown/null`。包裹标识、运单文字等观察值必须进入程序侧受信比对，模型不得自行宣称“与订单一致”。

### 5.3 身份属性与描述属性

身份定义属性默认包括：

- 商品角色/款式。
- 系列。
- 版本，例如国版/日版。
- 实物形态，例如圆角卡/方角卡。
- 必要附件或套装构成。

描述属性默认包括：页面尺寸、普通文字描述、拍摄角度、颜色受光变化、光栅图在不同角度呈现的画面。只有甲方版本化规则明确该描述字段定义 SKU 时，程序才可把它升级为身份属性。

因此：

- 页面写 20cm、实物包装写 80mm，但角色、系列、包装和 SKU 身份一致，转商品信息/货不对版，不判错发。
- 用户认为应收日版，但订单活动明确是国版且实收也是国版，未发现错发。
- 同一基础 SKU 的应发基准明确为圆角卡，实收为方角卡，形态属性冲突仍可构成错发。

## 6. 程序确定性决策

Gemini 输出完成后，程序按受信数据计算，不让模型直接给换货/退款结论。

### 6.1 差异计算

先按 `package_ref + identity_attributes` 聚合数量，再计算：

```text
missing_expected = expected - received
unexpected_received = received - expected
identity_conflicts = 同一应收映射下的身份属性冲突
```

总件数相同不能证明发对。典型替代型错发是“少一个应收款，多一个未购款或重复款”；必须同时展示缺失侧和多出侧。

### 6.2 决策表

| 条件 | 发错货事实倾向 | 材料状态/路由 |
| --- | --- | --- |
| 同包裹链可靠；全部实收可识别；应收商品缺失且出现未购商品，或身份属性明确冲突；规则不允许该差异 | 支持发错货 | 视频是否可直接终态见待甲方确认；需仓库时转终核 |
| 静态三类材料齐全；身份差异明确；尚无可追溯仓库实际打包记录 | 强差异事实，不能伪装仓库已确认 | `complete`，转人工/仓库核验 |
| 商品差异可见，但面单不匹配、未展示面单、视频分段、实收未展开或静态链不完整 | 证据不足；可单列“高度疑似” | `incomplete/indeterminate`，给唯一补件动作 |
| 仅缺应收商品，未发现错误商品 | 不在发错货终态内 | 切换漏发货，按漏发双路线重新核验 |
| 身份一致，仅页面尺寸、普通描述或展示角度不同 | 未发现错发 | 转商品信息/货不对版 |
| 随机/隐藏/特典/版本规则未齐或适用性未知 | 待确认 | 补受信规则或人工核验 |
| 包裹不是本站/当前订单发出 | 当前订单归属不成立 | 证据不足或转来源核验，不能把画面商品记为当前订单实收 |
| 技术解码失败 | 不产生业务结论 | `system_error`，系统重试 |

### 6.3 仓库状态

```text
warehouse_check:
  state: not_available | pending | verified
  outcome: confirmed_wrong | confirmed_not_wrong | null
  source_ref, checked_at, record_version
```

只有能追溯到实际仓库记录的结论才能写 `verified`。客服说“已处理”、系统出现换货卡片、用户后来退款、annotation 写“已核实”，都不能代替仓库记录。当前真实甲方接口只允许 Mock 和契约说明，不得伪装已接入或已查询。

### 6.4 与最终动作解耦

事实结论、材料状态、仓库状态、最终经营动作是四个维度：

- 初始事实可以是证据不足，但人工后续仍可能换货或补偿。
- 确认错发后，最终动作可能因库存或用户选择变成换货、退货退款或补偿。
- 最终动作只能由甲方人工/受信业务系统给出，模型不能根据历史处理频率推断。

## 7. 与漏发货的场景切换

发错货的核心语义是“交付了另一身份商品或错误版本/形态”；漏发货的核心语义是“应发义务中存在缺口”。

切换规则：

1. `missing_expected` 非空且 `unexpected_received` 非空，或身份属性冲突：保留发错货。
2. `missing_expected` 非空，但没有发现未购/错误身份商品：切换漏发货。
3. 用户把套装标题、宣传组合、特典字样当成独立应发义务时，先用受信商品构成和活动规则解析；不能凭标题自行扩张应发清单。
4. 切换后不得沿用发错货的“静态差异”直接判漏发。漏发须重新生成其 `evidence_route` 和 `resolution_basis`，静态材料齐全通常只进入仓库待核验。
5. 一个工单同时存在替代和纯缺失时，按原子应收项分别保留场景结果，不能用整单单标签吞掉另一诉求。

## 8. 场景专属双层报告

### 8.1 第一层：客服可行动摘要

只显示：

1. 发错货事实倾向与证据确定性。
2. 当前材料是否齐全。
3. 仓库状态（仅当本案需要）。
4. 唯一下一步；没有动作时不填流程废话。

推荐表达：

- “当前订单应收款与同包裹实收身份存在明确冲突；材料齐全，等待仓库终核。”
- “发现替代型差异线索，但当前视频未绑定订单面单；请补交匹配面单且完整展示实收的连续开箱视频。”
- “实收商品身份与订单一致，争议为页面尺寸信息；请转商品信息售后。”

### 8.2 第二层：审核详情

只展开发错货专属内容：

- 订单/包裹归属与面单匹配结果。
- 应收清单及版本化来源。
- 实收清单、数量和身份属性。
- 身份差异、缺失项和多出项。
- 视频链或静态链逐项状态。
- 随机/隐藏/活动/版本规则及版本。
- 仓库状态、来源和未确认项。
- 每项真实证据回链；视频优先跳到原视频秒数，图片可放大。
- 冲突、技术边界和场景切换理由。

报告不得复用商品有伤的伤点、成因或严重度模板，不展示原始 JSON、内部枚举、原始个人字段、完整运单、内部路径、模型渠道、Key、Prompt、黄金标签或调试参数。

## 9. 禁止推断清单

- 禁止把用户说“发错了”直接写成实收不一致。
- 禁止把用户照片中的商品在缺少同包裹关系时记为当前订单实收。
- 禁止因最终换货、退款、补发或补偿，倒推初始视频合格或初始错发已确认。
- 禁止把仓库结论写成视频/图片观察；没有可追溯记录就写“无仓库结论”。
- 禁止用客服要求补视频反推原视频具体不合格原因。
- 禁止只核总件数，不核角色、系列、版本、形态和附件。
- 禁止只按颜色、画面排布、人物数量、用户圈内称呼或模糊包装猜 SKU。
- 禁止把页面尺寸、普通描述、拍摄角度或光栅变化单独判成错发。
- 禁止把“适用随机/隐藏规则”直接等同于发对；必须读取规则允许的实际差异范围。
- 禁止把同一基础 SKU 直接视为身份一致；本次承诺的版本、形态或配件仍需比对。
- 禁止把静态三类材料齐全写成仓库已错装；它通常只是核验入口。
- 禁止把开头多个邮包同框机械判为来源混杂；应追踪目标箱体是否连续。
- 禁止把单 SKU 唯一密封袋或唯一内包面单的例外泛化到多包、多袋、离框或分段视频。
- 禁止让 Gemini 猜应收基线、包裹归属、随机规则、仓库事实、责任或最终经营动作。
- 禁止依据 14 个已学习案例、历史业务粗估或任何小样本编写准确率、自动化率或商业百分比。

## 11. 开发验收最小矩阵

实现和测试至少覆盖以下正反例：

- 替代型错发：缺应收 + 多未购；总件数相同。
- 同基础 SKU、身份形态不同；描述尺寸不同但身份一致。
- 面单匹配与不匹配；视频无面单；静态面单无法绑定视频。
- 单 SKU 唯一密封袋例外的成立与不成立。
- 唯一内包面单例外的成立与多内包/离框反例。
- 全部实收可识别与仍在包装中不可识别。
- 静态三类齐全进入仓库待核验，与缺一项的补件路径。
- 随机/隐藏/特典规则允许、禁止、未知三态。
- 只缺不多时切换漏发；同时存在替代与纯缺失时逐项保留。
- 仓库 `not_available/pending/verified`，以及后续动作不得倒推初始事实。
- 技术失败进入 `system_error`，不能伪装材料缺失。
- 第一层摘要、第二层证据详情同源，公开字段完成脱敏。

验收必须使用冻结、未泄题的黄金 Case 运行真实 API/Web 链路；已学习案例只能做回归。不得用 fixture、Mock 或静态检查替代真实媒体与正式接口验收，也不得由小样本推导准确率。

## 12. 待甲方确认与待复核

### 12.1 唯一业务规则待确认

完整、合规、同包裹且能识别全部实收的视频，是否在所有商品品类都允许程序直接形成“确认错发/未发现错发”终态，还是部分品类、随机规则或高价值商品仍必须查询仓库。甲方确认前采取保守策略：程序可输出高确定性的视觉事实倾向；命中需仓库品类或规则不明确时转人工/仓库，不自动执行经营动作。

### 12.2 资料冲突待复核

- 核对表个别单元格与 2026-08-13 定稿 HTML 不一致，例如 `310714` 的初始错发事实、`613280/615099` 的 `itemMismatch`。按上位契约，本文无权自行选择一方覆盖另一方；这些 Case 暂停作为自动化终态金标，仅保留为冲突回归样本，由甲方逐字段复核后再恢复。
- 定稿 HTML 的 `604382` 使用了“客服核实后确认换发版本”作为闭环依据，而综合契约要求仓库事实必须可追溯。生产实现应把“业务核实版本事实”和“仓库实际打包事实”拆为不同来源类型；甲方未确认来源权威等级前，不能泛化为所有同类案例的仓库终核。
- `56790` 已被现行综合契约除名；任何历史 HTML 或表格残留都不能重新纳入盲验或完成度统计。
