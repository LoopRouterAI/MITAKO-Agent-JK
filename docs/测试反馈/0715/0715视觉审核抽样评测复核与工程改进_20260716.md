# 0715 视觉审核抽样评测复核与工程改进

版本日期：2026-07-16
适用范围：MITAKO 视觉审核服务、甲方下一轮抽样测试、双方技术沟通

## 1. 结论先行

甲方 0715 的测试方法适合作为一次探索性回归和接口链路检查，但当前 `44.12%` 三分类一致率不能直接表述为系统的生产准确率，`3.23%` 也只能表述为“当前标签口径下，人工负向样本被系统精确判为 negative 的比例”。主要原因不是否认测试结果，而是评测问题、输入上下文和路由含义尚未完全对齐：

1. 甲方人工分类可能包含退款、换货、补发等最终业务处置；系统标签回答的是“现有视觉材料是否支持用户诉求”。两者不是天然同义。
2. 本轮主要上传媒体文件，未完整提交订单商品、SKU、仓库主数据、用户诉求、对话和 SOP。发错货、漏发货、未成年人退款尤其依赖这些上下文。
3. `review` 是证据不足后的人工复核路由，不等同于自动放行，也不等同于自动拒绝。
4. 102 个可比样本能够暴露问题，但每个场景和类别的样本较少，且 413/415 与超大文件跳过造成输入选择偏差。

因此，当前结果必须保留并认真整改，但应称为“与当前人工分类的探索性一致率”，不能单独作为生产能力裁决。

## 2. 甲方测试方法哪些是正确的

- 固定随机种子并分层抽样，可复现。
- 标签未传入模型，符合盲测隔离要求。
- 通过标准服务接口批量创建异步任务，方向正确。
- 保存逐样本结果、原始响应和失败清单，具备追溯基础。
- 使用混淆矩阵，而不是只给总体准确率。
- 将 413、415 单独记录，暴露了网关和输入格式问题。

这些做法应保留到下一轮。

## 3. 当前统计应如何解释

根据报告中的 102 个可比样本：

- 人工正向 37：系统 positive 21、negative 1、review 15。
- 人工负向 31：系统 positive 13、negative 1、review 17。
- 人工不确定 34：系统 positive 9、negative 2、review 23。
- 三分类完全一致 45/102，即 44.12%。

对人工负向样本，至少应同时展示：

- 精确 negative 召回：1/31，即 3.23%。
- 负向误接纳风险：13/31，即 41.94%。
- negative 或 review 安全路由：18/31，即 58.06%。

其中真正需要最高优先级处理的是“人工负向被系统判为 positive”，而不是把 `review` 与 positive 合并为同一种风险。

## 4. 对我方回复的专业性复核

原回复中以下方向合理：

- 先由甲方确认一批标签语义清晰的正向、负向和需复核样本。
- 抽帧频率允许配置，并支持 1 FPS、2 FPS 等更高强度。
- 可疑帧无论证据充分或不足，都应进入 HTML 报告并解释其作用。
- 低置信结果转人工，不自动作最终业务处置。

需要修正的表述：

- 不宜说“50 个正向和少量负向”。负向是误放行风险最大的类别，不应只准备少量负样本。
- 不宜提前承诺“提示词改动空间不大”或“工程置信度足够”，结论必须由冻结样本的复测数据支持。
- 加密抽帧很重要，但不是唯一因素。订单/SKU 上下文、素材完整性、非 AI 时间轴取证、反证检索和路由阈值同样会影响结果。
- 转人工不仅由低置信触发，还应包含模型结论为 review、支持与反证冲突、材料缺口、疑似剪辑、场景超出覆盖范围等情况。

## 5. 标签治理与运行时接口的正确边界

“至少两名标注者、仲裁、理由完整、证据充分”属于双方商定的评测数据治理建议，不是生产审核 API 的必填字段，也不能成为审核任务的运行时硬门槛。

项目侧必须做到：

- 接受甲方当前能提供的案件字段和素材。
- 没有双人标注也照常创建和执行审核任务。
- 生产审核请求不携带人工答案；发现 `ground_truth` 等评测标签时继续拒绝，防止泄题。
- 离线统计工具只在推理完成后关联人工标签。
- 报告明确人工标签质量是外部前提，不擅自替甲方裁决标签。

甲方侧可选建议：争议样本或高风险样本再复核或仲裁；不要求全部生产案件双人标注。

## 6. 审核强度设计

建议保留五种兼容档位：

| 档位 | 抽帧策略 | 典型用途 |
|---|---|---|
| adaptive | 全时间轴低成本自适应抽帧，按时长和文件大小控制预算 | 默认批量初筛 |
| strong | 固定 1 FPS，按 24 帧分段并行 | 有疑点、重视连续性的案件 |
| strict | strong 的兼容别名 | 兼容现有调用方 |
| forensic | 固定 2 FPS，并结合非 AI 取证信号 | 高风险、疑似剪辑或反证冲突 |
| custom | 甲方自定义 0.1-2 FPS、帧上限和分段大小 | 特殊场景与成本控制 |

1 FPS 有助于观察视频连续性和显著跳切，2 FPS 更适合对疑点区间复核；但任何抽帧密度都不能单独证明视频未剪辑。需要组合容器/流元数据、时间轴、音视频时长差、帧率和编码信息、可疑画面突变及模型跨帧判断。

自动升级应先返回“推荐升级计划”，并说明触发原因和预计帧数/分段/成本。未经甲方成本策略授权，不应无上限自动重复调用更强档位或更贵模型。

## 7. 下一轮非强制盲测建议

1. 双方先确认评测问题：“当前材料及业务上下文是否支持用户诉求”。
2. 甲方可由一名熟悉 SOP 的人员标注；争议或高风险样本可选复核，不作为 API 要求。
3. 通过离线 `case_id` 关联标签，推理请求中不出现人工答案、标签目录名或预期结论。
4. 标准组提交完整 metadata 和全部素材；另设“仅媒体输入”降级组，二者分开统计。
5. 固定代码版本、审核档位、模型配置、随机种子和样本集。
6. 分别报告工程指标、模型指标和风险指标。
7. `review` 单独统计为人工复核路由。
8. 413/415 和超大文件处理计入端到端成功率，不进入成功推理样本的模型准确率分母。
9. 正式阈值由双方根据误放行成本、人工节省目标和场景风险协商，不由代码单方面制定。

## 8. 工程整改验收点

- 审核档位对 API 可见且向后兼容。
- 报告显示支持证据、反证/可疑帧、时间戳、材料缺口和置信度理由。
- 非 AI 取证只输出“风险信号”，不伪装成剪辑事实。
- 可疑案件输出升级建议、预计帧数和成本影响。
- 离线评测输出混淆矩阵、每类召回/F1、人工复核率、自动判定覆盖率、负向误接纳风险和置信度校准。
- 客服 Agent、私域 Agent 的演示数据与真实甲方联调边界明确。
