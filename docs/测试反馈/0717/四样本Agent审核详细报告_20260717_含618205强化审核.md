# MITAKO 视觉审核 Agent 四样本定向审核详细报告

测试时间：2026-07-17  
测试入口：`POST https://agent.deeptokenai.cn/api/v1/review/jobs`  
登录账号：`admin / admin123`  
测试场景：商品有伤审核 `product_damage`  
测试样本：617341、614176、618205、617911  
输入策略：仅提交样本文件夹中的图片、视频媒体文件；不提交 `annotation.json`、`reply.json` 等包含人工结论的文件，避免污染 Agent 判断。  

## 一、总体结论

本轮对 4 个重点样本进行了 Agent 审核复测。需要特别说明：本报告不只按“是否与人工标签一致”评价 Agent，而是同时关注用户最初诉求、Agent 实际拿到的上下文、人工标签本身是否合理，以及最终是否能形成更好的客服体验。

- 617341、617911 两个明确负样本均被 Agent 判为 `review/uncertain`，没有自动判负。
- 614176 在当前评测 manifest 中被标为负样本，但复查 `content.txt` 和 `reply.json` 后，该负样本标签存在明显争议：用户最初诉求是“鼓包、撞角、缝线歪了”，人工客服多次生成售后补偿方案，后续才在长轮沟通中出现“撕拉拍立得”相关诉求。因此不应简单把 614176 视为 Agent 漏识别“自己撕坏”。
- 618205 普通审核仍被 Agent 判为 `positive / 0.95`，与人工“视频不完整、出框时间长、应补证”的口径不一致。
- 之后使用新增的 strong 强化审核配置重新审核 618205，Agent 结果从 `positive / 0.95` 改为 `review / 0.69`，并识别到开箱完整性不完整、争议商品离镜等问题，方向与人工口径基本一致。

从结果看，新版 Agent 已经具备更保守的风险识别能力。普通审核链路仍无法稳定完成“明确负样本自动拒绝”和“开箱完整性异常识别”。但 614176 更应被看作“人工标签/评测口径需要修正”的样本，而不是 Agent 明确漏判。强化审核对 618205 有明显改善，但服务端媒体取证能力未完全生效，返回 `ffprobe_not_available`，说明部署环境或后端依赖仍需补齐。

## 三、单样本详情

### 1. 617341

人工标签：`negative`  
人工原因：无开箱，暴力运输  
Agent 普通审核结果：`review/uncertain`  
置信度：`0.69`  
是否进入人工：是  
任务号：`RJ-5060443172F14E30`  
送审素材：0 个视频，8 张图片，约 23.01MB  

Agent 关键判断：

- 图片中可见外包装箱存在明显变形。
- 图片中部分纸质商品/拍立得卡片存在弯曲。
- 未提供完整开箱视频，因此开箱完整性无法确认。
- Agent 给出的业务动作是“需要 VIP 客服复核”，而不是直接判负。

与人工标签对比：

- 人工标签为负样本，核心原因是“无开箱视频”不满足售后举证要求。
- Agent 虽然识别到缺少开箱视频，但没有把该条件转化为自动拒绝，而是进入人工复核。

问题判断：

如果业务规则中“商品有伤必须提供完整开箱视频”是硬性条件，则该样本应由 Agent 直接输出 `negative`。目前 Agent 的结果更像“证据不足，需要人工确认”，会导致低价值负样本继续占用人工客服。

建议：

- 将“无开箱视频且规则要求开箱视频”的场景配置为明确负样本条件。
- 在报告中单独输出字段：`opening_video_required=true/false`、`opening_video_present=true/false`、`auto_reject_reason=missing_required_opening_video`。

### 2. 614176

当前 manifest 人工标签：`negative`  
当前 manifest 人工原因：有开箱，但明显自己撕坏  
标签复查结论：该负样本标签存在争议，不应直接作为 Agent 错判依据。  
Agent 普通审核结果：`review/uncertain`  
置信度：`0.69`  
是否进入人工：是  
任务号：`RJ-020540014A374295`  
送审素材：1 个视频，20 张图片，约 643.81MB  

样本上下文复查：

- `content.txt` 中用户最初诉求是：“43s开始，鼓包＋撞角＋缝线歪了，品控问题，不接受换货，退货退款”。
- 用户最初诉求没有提到“撕拉片/撕拉拍立得被撕坏”。
- `reply.json` 显示人工客服在长时间沟通过程中多次生成“售后补偿方案已生成，请确认”，说明人工客服对用户最初的品控诉求至少不是直接拒绝。
- “撕拉拍立得和娃退货退款”是在后续长轮沟通中出现的扩展诉求，不是 Agent 本次送审时 `customer_claim` 中的核心问题。

测试过程补充：

- 批量提交时曾返回 `413 Request Entity Too Large`。
- 随后对 614176 单独重跑成功，说明服务并非完全不能处理该体积素材，但上传链路或网关限制仍存在不稳定。

Agent 关键判断：

- 开箱过程基本连续，未发现明显调包。
- 视频和图片中确实存在用户反馈的缝线、鼓包、撞角等异常。
- Agent 认为这些异常是否达到棉花娃娃售后标准，需要人工结合品类规则判断。
- Agent 审核范围与用户最初诉求一致，聚焦“缝线、鼓包、撞角”，没有围绕后续才出现的“撕拉拍立得”进行裁决。

与人工标签对比：

- 当前 manifest 将该样本标为负样本，原因是“有开箱但明显自己撕坏”。
- 但从用户最初诉求和 `reply.json` 看，人工客服曾围绕“鼓包、撞角、缝线歪”等品控问题持续沟通补偿方案。
- 因此，若评测目标是审核用户最初提交的视频/图片是否支持“娃娃缝线鼓包等品控问题”，Agent 输出“视觉上确有异常，但是否达到售后标准需人工复核”是合理的。
- 不应把“未识别撕拉片明显自己撕坏”记为 Agent 漏判，因为该信息没有出现在本次 `customer_claim` 中，也不是最初诉求。

问题判断：

该样本更主要暴露的是“评测标签口径”和“多轮客服上下文切分”的问题，而不是 Agent 视觉能力不足。用户最初反馈的娃娃缝线、鼓包、撞角问题，与后续出现的撕拉拍立得退货退款诉求，并不一定应该合并成同一个负样本结论。Agent 当前只拿到最初诉求和媒体材料时，未审核撕拉片细节属于正常。

如果目标是最优客服体验，Agent 需要区分：

- 用户当前正在申诉的主诉求是什么。
- 后续新增诉求是否属于同一商品、同一问题、同一证据链。
- 人工最终标签是否只因为后续某个子诉求不成立，而覆盖了前面已经被认可的主诉求。

建议：

- 将 614176 从“明确负样本”改为“标签争议样本/主诉求可能成立但售后方案争议样本”，不建议纳入负样本准确率统计。
- 后续样本标签应按“主诉求”和“新增诉求”拆分，而不是用最终人工备注覆盖整个工单。
- Agent 报告中应增加 `claim_scope` 字段，明确本次审核的是“娃娃缝线鼓包”还是“撕拉拍立得损坏”。
- 如果要让 Agent 审核后续新增的撕拉片问题，必须把对应文本、图片、视频和诉求一起提交给 Agent。
- 排查大文件上传限制，确保 nginx、应用服务、multipart 解析层的限制一致。

仍存在的问题：

- 强化审核的媒体取证模块未真正执行，返回 `media_forensics.status=unavailable`，原因是 `ffprobe_not_available`。
- 这意味着容器完整性、码流一致性、帧率一致性、packet timeline、editor metadata 等取证项没有生效。
- 报告文本内部存在局部矛盾：一处写“视频在第 24 帧 00:11.44 即结束”，但对象跟踪又识别到争议商品在 `00:52.22` 首次曝光。说明多段审核结果的聚合摘要仍需修正。

建议：

- 对开箱视频完整性审核默认启用更高频抽帧或在低置信时自动升级 strong。
- 部署环境补齐 `ffprobe` 或等价媒体分析工具，使媒体取证链路真正可用。
- 修复报告聚合逻辑，避免不同分段的结论被拼接后产生自相矛盾。
- 普通审核不要只看“图片中是否有伤”，必须先判断“图片中的伤是否能通过开箱视频绑定到本次包裹中的同一件商品”。

## 四、问题优先级

### P0：普通审核对 618205 的开箱完整性判断仍不可靠

普通审核仅送审 10 帧，未识别“视频不完整、出框时间长”，反而以 0.95 高置信判正。该问题会直接影响开箱视频审核可信度。strong 强化审核能改善该问题，说明普通审核的抽帧密度和连续性判断不足。

### P0：明确负样本无法稳定自动判负

617341、617911 是更明确的负样本，但 Agent 都输出 `review/uncertain`。如果业务目标是减少人工客服，必须将一部分明确负样本从“转人工”推进到“自动拒绝”。614176 不建议继续作为明确负样本引用，因为该样本的负样本标签与用户最初诉求、人工客服补偿过程存在冲突。

### P1：样本标签与用户诉求范围需要拆分

614176 不能简单归因为 Agent 未识别人为损坏。更准确的问题是：工单中出现了多个诉求阶段，人工最终备注中的“明显自己撕坏”可能对应后续新增的撕拉拍立得诉求，而 Agent 本次审核的是用户最初提出的娃娃鼓包、撞角、缝线歪问题。后续评测需要按诉求拆分样本，避免用后续子诉求的人工结论否定前置主诉求的视觉审核结果。

### P1：强化审核依赖未完整部署

618205 strong 审核返回 `ffprobe_not_available`。说明新增取证能力在当前部署环境中没有完全生效。若要将强化审核用于线上低置信兜底，必须补齐服务端依赖。

### P1：报告聚合存在自相矛盾

618205 strong 报告中同时出现“视频在 00:11.44 结束”和“争议商品在 00:52.22 首次曝光”。这类矛盾会影响客服或产研对结果的信任。

### P2：大文件上传链路仍需稳定性验证

614176 首次批量提交 643.81MB 返回 413，单独重跑成功。需要统一网关和应用层文件限制，并做多次重复上传验证。

## 五、给产研的迭代建议

1. 普通审核增加开箱完整性前置门槛：先判断证据链是否完整，再判断商品是否有伤。
2. 对低置信、争议商品离镜、视频中未展示核心实物的样本，自动升级到 strong 强化审核。
3. 明确负样本自动判定规则，优先覆盖“无开箱视频”“完整视频看不出伤”等主诉求明确、证据链明确的场景。
4. 对多轮工单增加 `claim_scope` 和“主诉求/新增诉求”拆分能力，避免把后续新增问题的人工结论错误套用到最初诉求。
5. 补齐 `ffprobe` 或等价媒体取证工具，确保强化审核中的容器、码流、帧率、时间线取证真正生效。
6. 修复报告聚合逻辑，避免不同分段结论拼接后出现矛盾。
7. 对 600MB 以上视频做连续多次上传测试，确认 nginx、应用服务和对象存储链路限制一致。
