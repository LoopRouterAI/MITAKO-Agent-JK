## 视频传输决策

### 百度文档事实

本地文档 `docs/各API开发文档/BG模型.md` 明确说明：小文件使用 `inlineData`，大文件使用 `fileData.fileUri`，百度渠道无需先调用 Google Files API。该文档没有给出百度 `fileUri` 的 100 MB 上限。因此不得把 Google 官方外部 URL 的 100 MB 限制未经验证地套用到百度渠道。

### 目标路由顺序

1. 请求总载荷在内联安全预算内时，原始视频不转码，直接 `inlineData`。
2. 超过内联安全预算时，原始视频优先通过受控 HTTPS URL 作为 `fileData.fileUri` 提交。没有既有公网对象存储地址时，使用临时 Cloudflare Tunnel 暴露专用媒体端点。
3. 不预设百度 URL 大小上限。先真实提交 88.7 MB 的 588609 原片和 279.5 MB 的 587966 原片；记录 HTTP 状态、供应商错误、请求 ID、耗时和 token。只有百度明确拒绝文件大小、编码或下载时才进入回退。
4. URL 回退仍失败时才转码；转码后仍优先走 URL，不为了 Base64 预算主动降低视觉质量。
5. 供应商明确要求分段时才分段。分段必须覆盖完整时间轴并保留全局时间戳，不允许使用人工已知问题窗口裁剪。

### Cloudflare 临时隧道安全边界

- 本地媒体服务只绑定 `127.0.0.1`，公网只暴露一个随机、短时有效的签名媒体 URL。
- 只允许 `GET`、`HEAD` 和必要的 Range 请求；不提供目录列表，不暴露样本目录、工单标签、`annotation.json`、`reply.json`、Prompt、Key 或报告。
- URL 使用不可预测随机令牌和过期时间；审核完成或失败后立即停止隧道与本地媒体服务。
- 日志只记录脱敏 URL、文件字节数、SHA-256、传输状态和请求 ID，不记录完整签名 URL。

## 专业保真转码策略

当前实现的 `scale=960:1280:force_original_aspect_ratio=decrease,fps=10` 会把 1920×1080 横屏视频实际降为约 960×540，并用 H.264 CRF 26/2 Mbps 编码。这会损失划痕和快速动作细节，不能继续用于模型公平选型。

新的回退梯度如下：

1. 不升采样；源视频不高于 2K 时优先保留原分辨率，源视频高于 2K 时先限制在 2560×1440。
2. 帧率取 `min(源帧率, 24 FPS)`；不得再降为 10 FPS。音频保留，HEVC/MP4 使用 AAC，VP9/WebM 使用 Opus。
3. 第一候选为 HEVC/H.265 MP4，使用兼容的 8-bit `yuv420p`；第二候选为 VP9 WebM。选择必须经过百度真实解码验证，不能只依据本地 FFmpeg 可生成。
4. 先在 2K/原分辨率尝试质量优先编码；仅当真实供应商限制仍无法满足时才降到 1920×1080。不得低于 1080P，除非甲方另行批准或源视频本身低于 1080P。
5. 每个代理必须校验完整时长、分辨率、帧率、音轨、字节数、可解码性和 SHA-256，并在实验报告中同时记录源文件与代理参数。

## Schema 与单轮多任务设计

原始“单轮完成多种视觉审核任务”要求继续有效。问题不在单轮多任务本身，而在旧返回结构把视觉事实、客服报告、流程建议、人工路由和业务动作混成约 12,549 字符、15 个顶层块的报告型 Schema。

本轮保留两组公平对照：

- 感知型 Schema：单轮返回 9 个甲方标签、争议商品身份与展示窗口、速度判断、伤点事实及少量可回链证据。完整客服报告由确定性规则和渲染器生成。
- 完整旧 Schema：在同一原片、同一模型、同一 `thinkingLevel`、同一 `mediaResolution` 和 65,536 输出上限下作为对照，验证更强思考是否足以解决复杂结构问题。

选型以业务事实准确性和内部一致性为第一指标；成本、耗时和 token 为第二指标。即使完整 Schema 在强模型上可运行，只要它持续产生截断、字段矛盾或不必要的报告生成负担，生产路径仍应采用感知型 Schema。

## 当前进度与中断点

已完成：

- 当前生产默认模型仍是 `gemini-3.5-flash-lite`，百度渠道优先。
- 已支持 Gemini 3.6 Flash、`thinkingLevel`、`mediaResolution` 和显式 `maxOutputTokens`。
- 已新增约 2,759 字符的感知型 Schema；保留旧完整 Schema用作对照。
- Medium/High 实验档输出上限已从 16,384 调整为 65,536；相关聚焦测试为 `23 passed`。
- 已确认 588609 原片是 1920×1080、30 FPS、HEVC、88,691,265 字节；旧代理为 8,310,420 字节，输入质量不公平。
- 已确认本机 FFmpeg 支持 `libx265`、`libvpx-vp9` 和 Intel Quick Sync HEVC；不得使用不存在的 NVIDIA CUDA 作为默认路径。

作废或待重跑：

- 587966、588609、609768 先前使用 960×540/10 FPS 代理得到的模型结果不能作为最终选型结论。
- 588609 的 65,536 上限重跑在发起 API 前因 Windows 后台命令未正确引用带空格路径而退出，没有产生有效供应商请求或费用。

唯一下一步：先实现并安全验证“原片 inline / 原片 CF URL / 2K 至 1080P 保真转码回退”的传输链；随后盲跑三个 Case 的 Gemini 参数与 Schema 矩阵。传输公平性未通过前，不发布模型胜负结论，也不切换生产默认模型。
