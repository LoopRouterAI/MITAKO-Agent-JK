02 多 Agent 对抗式审查结论

二次元谷子客户视角 没有真实“群成员在企微群里被 Agent 服务”的体验；当前是后台手动表单，不是企微读群、发群、会话存档或群发。吃谷雷达只是候选结果，没有触达、点击、订单归因。
产品经理/验收视角 可作为“POC 演示 + 接口契约 + Mock 准备态”，不能作为“真实甲方系统已接入、1 万群运营已落地、A/B 已上线”验收。
技术集成/合规视角 企微、飞书 CLI、商品库、订单/物流/仓库/财务/售后、CRM/CDP、OneID、真实向量库均未接入。现有接口是本地契约。
主审计补充：客服主管 + CGO 舆情只看单条关键词，没有上下文窗口、多人共振、主管预警闭环；增长闭环只有“商品事件 -> 候选”，没有许愿池、蹲守提醒、点击/下单/退群反馈。

06 甲方群、商品事件到底如何打通

当前真实情况

现在的打通方式只有“手动表单或 HTTP 调用本地 POC 接口”。没有企微、飞书、商品中心、订单中心生产连接。要变成甲方可试点系统，需要按下面的最小路径接。

1. 企微入站 企微会话存档 / SCRM webhook / 导出文件，把群消息规范化。
2. 调用群消息接口 POST /private-domain/group-message，字段含 group_id、external_user_id、content、message_id。
3. 本地决策 规则快筛、风险等级、禁推、客服任务、候选回复。
4. 人工审核 营销/安抚文案过 Guard 和运营审核，不直接自动群发。
5. 企微出站 调用企微群发或客服私聊接口，写回 trace_id、send_id。

飞书 CLI / 飞书任务建议

飞书不应直接做业务执行。最小用途是“人工审核和协同”：把高风险群、客服任务、商品推送候选同步到飞书表格或任务，字段为 task_id、owner、status、trace_id、due_at、result。CLI 只做离线同步和日报生成，所有退款、补发、群发仍回到业务后台审批。
