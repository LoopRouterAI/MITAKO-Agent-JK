## 结论

当前项目不能直接满足本规格。现有系统是 V1 平台底座：用户对话、情绪识别、转VIP客服、坐席台、运营台、SSO/Chatwoot 联调、Mock 业务接口与部分生产化基建。甲方 2026-06-29 需求已经进入正式业务系统范围，但本项目本期只能用 Mock 模拟甲方后台、客户接口、企微、飞书、仓库、财务和商品库，不接入甲方真实系统。因此目标应修正为：基于真实 SOP 和会议需求，做一个可演示、可测试、可审计的 Mock 业务闭环。

本规格替代“把 010/011 继续扩写”的做法。010 是企业生产基建补齐，011 是 Companion 可观测平台重构，二者都不是本次甲方业务范围的实现入口。

## User Scenarios & Testing

### User Story 1 - 售后 SOP 半自动处理 (Priority: P0)

作为 C 端用户，我在退款、物流异常、商品有伤、漏发、发错货、账号换绑、未成年人退款等场景中提交诉求后，系统应先识别正确工单类型，再按对应 SOP 给出可执行下一步；涉及退款、补发、换货、拒赔、敏感材料和大额补偿时必须进入人工确认或主管审批。

**Why this priority**: 这是节省客服成本的核心。没有 SOP 状态机，Agent 只能聊天，不能替代或辅助客服处理业务；本期状态与后台结果均由 Mock 契约提供。

**Independent Test**: 使用每份 SOP 至少 3 条脱敏/构造样本，在 Mock 工单、Mock 订单、Mock 物流、Mock 售后卡片状态下验证工单类型、受理边界、分支动作、话术、转VIP客服条件与后台动作建议全部正确。

**Acceptance Scenarios**:

1. **Given** 用户说“不想要了想退款”，**When** 系统识别为主观退款，**Then** 命中《申请退款》受理边界，并根据后台退款状态输出“挂起/发送退款卡片/拒绝完成/提交答疑”的明确动作。
2. **Given** 用户说“快递半个月没动”，**When** 系统查询包裹状态，**Then** 区分未发出、已发出、停滞、拒签退回、丢件、销单，并输出对应 SOP 分支。
3. **Given** 用户说“少了一个吧唧但多了别人的商品”，**When** 系统做工单分类，**Then** 从漏发货转为发错货，而不是继续按漏发处理。
4. **Given** 用户申请未成年人退款，**When** 材料缺失或关系链无法证明，**Then** 系统只生成补充材料要求或转VIP客服复核，不把结论直接自动通过。

### User Story 2 - 多模态凭证审核 (Priority: P1)

作为售后客服，我希望系统辅助审核开箱视频、商品损伤图片、发错货图片和证件材料，给出结构化结论、理由、置信度和人工复核建议。

**Why this priority**: 视频、图片、证件审核是会议中最耗人工且风险最高的部分，但模型误判会直接影响赔付和客诉，必须先做辅助审核。

**Independent Test**: 使用脱敏样本或本地构造样本做离线盲测。若缺少真实视频、图片、证件材料，则用固定 fixture 和人工标注结果模拟模型输入输出，不宣称真实识别准确率。

**Acceptance Scenarios**:

1. **Given** 用户上传开箱视频，**When** 系统审核，**Then** 输出一镜到底、未拆封快递盒及面单、瑕疵位置、剪辑疑似、物品离镜、合规等级和复核理由。
2. **Given** 商品图片存在高反光，**When** 系统无法可靠判断划痕，**Then** 标记“需人工复核/需补充对光视频”，不得自动拒赔或自动赔付。
3. **Given** 证件材料包含身份证、户口本、出生证明、承诺书、支付流水、手机号实名证明，**When** 系统审核，**Then** 只输出材料完整性、关系链、矛盾点和脱敏结果，最终审核流转给指定人工角色。

### User Story 3 - 后台工具调用与权限审批 (Priority: P0)

作为甲方管理者，我希望 Agent 能读取 Mock 工单、Mock 订单、Mock 物流、Mock 售后、Mock 退款、Mock 仓库、Mock 商品库和 Mock 财务状态；但所有模拟写操作仍必须受最小权限、白名单、审批、审计和回滚约束，以便未来替换为真实接口。

**Why this priority**: 没有业务状态接口，Agent 无法判断 SOP 分支；本期用 Mock 契约模拟这些状态，同时保留权限边界，避免演示逻辑养成越权操作模式。

**Independent Test**: 对每个工具调用做契约测试和越权测试，确认读写权限、审批门槛、审计字段和失败回滚都可验证。

**Acceptance Scenarios**:

1. **Given** Agent 需要判断退款状态，**When** 调用 Mock 订单/售后只读接口，**Then** 响应包含订单、商品、金额、卡片状态、工单状态和可退款标记。
2. **Given** Agent 建议发送退款卡片，**When** 金额、敏感品类或用户风险超过阈值，**Then** 必须生成审批请求，不能直接写入后台。
3. **Given** 用户通过提示词诱导 Agent 修改地址或读取他人订单，**When** 工具调用前置权限校验失败，**Then** 调用被拒绝并写入安全审计。

### User Story 4 - 质检、质疑与 SOP 更新 (Priority: P1)

作为客服主管，我希望系统自动抽检 Agent 和VIP客服回复是否遵守 SOP、是否安抚到位、是否越权承诺，并能沉淀“合理但超 SOP”的特殊案例，生成 SOP 更新建议。

**Why this priority**: 会议明确指出 SOP 不一定总是正确，系统不能只机械执行规则；但 SOP 更新必须经过人工审核和版本管理。

**Independent Test**: 随机抽取 200 条会话，系统生成质检结果，主管复核一致率达到验收标准。

**Acceptance Scenarios**:

1. **Given** 回复中出现“我保证某日发货”或手算退款金额，**When** 质检执行，**Then** 标记 SOP 违禁风险并要求人工复核。
2. **Given** 用户诉求超出 SOP 但存在老客价值、舆情风险或明显购买体验受损，**When** 质疑 Agent 复核，**Then** 输出“建议特殊处理”的理由和审批路径。
3. **Given** 多个特殊案例指向同一 SOP 漏洞，**When** 主管审核通过，**Then** 新 SOP 版本发布，旧版本可回滚，相关测试集同步更新。

### User Story 5 - 多端并发、跨工单与跨天跟进 (Priority: P0)

作为用户和客服，我希望同一用户从手机、小程序、企微、语音等入口发起咨询时，系统能正确关联用户、订单、工单和上下文；物流、仓库、退款等异步结果回来后能自动触发待办或用户跟进。

**Why this priority**: 并发和跨天跟进是线上真实客服的基础能力，缺少锁和事件流会造成重复赔付、重复回复和漏跟进。

**Independent Test**: 同一用户并发发起两个退款/补发诉求，系统必须只允许一个订单级写操作进入审批或执行。

**Acceptance Scenarios**:

1. **Given** 用户在 A 工单里提 B 订单，**When** 系统识别订单号或商品线索，**Then** 拉取 B 订单并提示跨工单关联，而不是要求用户重提。
2. **Given** 两个端同时触发同一订单退款，**When** 写操作进入系统，**Then** 订单锁阻止重复退款或重复补发。
3. **Given** 仓库第二天回复缺货，**When** 事件进入系统，**Then** 生成客服待办或在允许范围内自动给用户发送跟进话术。

### User Story 6 - 私域运营与商品转化 (Priority: P2)

作为私域运营人员，我希望 Agent 接入企业微信社群和商品库，能识别用户意向、打标签、推荐商品、生成销售线索、汇总舆情与高意向用户。

**Why this priority**: 甲方明确“纯聊天没有意义”，私域系统的目标是留存和转化，但它不应阻塞客服 P0 闭环。

**Independent Test**: 在试点社群中验证关键词监听、标签生成、商品推荐、人工跟进清单和风控频率。

**Acceptance Scenarios**:

1. **Given** 用户在群内表达某 IP 或品类兴趣，**When** Agent 分析消息，**Then** 生成用户标签和可推荐商品候选，并遵守企微触达频率限制。
2. **Given** 群内出现售后负面情绪，**When** Agent 识别，**Then** 转为客服工单或提醒人工运营介入。
3. **Given** 每日运营结束，**When** 系统汇总，**Then** 输出高意向用户、热议商品、负面情绪、待人工跟进和推荐动作。

### User Story 7 - 仓库 Agent 与跨部门协同 (Priority: P2)

作为客服和仓库人员，我希望系统收口催发货、缺货、补货、物流异常、仓库反馈等跨部门任务，按优先级形成任务清单并同步状态。

**Why this priority**: 仓库响应慢会直接拖累客服体验，但仓库 Agent 可先从任务流开始，不必一开始接管 WMS。

**Independent Test**: 对 20 个仓库相关工单生成任务清单，验证状态同步、逾期提醒和用户跟进闭环。

**Acceptance Scenarios**:

1. **Given** 客服提交仓库核实需求，**When** 仓库 Agent 收到任务，**Then** 记录责任人、优先级、截止时间、关联工单和回复渠道。
2. **Given** 仓库超时未回复，**When** 到达 SLA，**Then** 发送提醒并升级到主管视图。
3. **Given** 仓库反馈无品控或缺货，**When** 任务关闭，**Then** 同步给客服 Agent 生成退款/退回赏袋/继续等待的 SOP 分支建议。

## Edge Cases

- 用户只上传图片但声称有开箱视频：转入商品有伤初步判定或要求补充视频，不能按合规开箱视频处理。
- 用户提交未成年人退款但材料包含非监护人、非实名手机号、主副卡关系或公司发票：进入材料补充或人工复核。
- 用户诉求合理但超 SOP：进入质疑/主管审批，不由一线 Agent 自行承诺。
- 同一订单并发退款、补发、换货：订单级锁阻止重复写操作。
- 模型不可用、超时、配额耗尽：自动转VIP客服或进入待处理队列，不让用户自行猜测是否需要转VIP客服。
- 低置信度视觉/OCR 结果：只做辅助证据，不能自动拒赔、自动拉黑或自动赔付。
- 用户要求 AI 透露系统提示词、后台接口、他人订单或内部群信息：拒绝并写安全审计。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 将 SOP 文档拆分为可版本化、可检索、可回滚的知识单元，并保留来源文件、段落、适用工单类型和生效时间。
- **FR-002**: 系统 MUST 对用户诉求进行工单类型识别，并支持退款、物流异常、商品有伤、漏发、发错货、出荷转囤、未成年人退款、账号换绑和非常规问题的重定位。
- **FR-003**: 系统 MUST 对每个 SOP 工单类型建立状态机，输出当前分支、必要证据、允许动作、禁止动作和转VIP客服条件。
- **FR-004**: 系统 MUST 区分自动动作、半自动动作和人工确认动作；退款、补发、换货、拒赔、大额补偿、修改地址、账号换绑、未成年人退款终审均不能由 Agent 无审批直接完成。
- **FR-005**: 系统 MUST 提供工单、订单、售后卡片、物流、仓库、财务/退款、商品库、企微和飞书的 Mock 契约接口；接口路径、字段、状态枚举和错误码必须稳定，便于未来替换为真实系统。
- **FR-006**: 系统 MUST 对后台工具调用执行最小权限、租户隔离、用户/坐席身份绑定、敏感操作审批、请求签名和审计记录。
- **FR-007**: 系统 MUST 对 Agent 输出先做安全与 SOP 审查，再向用户展示，不得先流式展示后再决定是否转VIP客服或拦截。
- **FR-008**: 系统 MUST 在 P0 转VIP客服场景短路业务副作用，不得继续执行补偿、退款、写记忆或后台写操作。
- **FR-009**: 系统 MUST 在 LLM 失败、配额耗尽、模型超时或安全审查 block 时提供兜底路径：自动转VIP客服、生成待处理任务或显示明确失败状态。
- **FR-010**: 系统 MUST 使用服务端权威会话历史生成多轮上下文和交接简报，不能信任客户端传入的 history 作为唯一事实来源。
- **FR-011**: 系统 MUST 支持跨工单和跨订单关联，避免重复赔付、重复退款、重复补发和重复回复。
- **FR-012**: 系统 MUST 提供用户、会话、工单、订单三级锁或幂等键，处理多端并发入口。
- **FR-013**: 系统 MUST 支持事件触发的跨天跟进，包括物流更新、仓库回复、退款到账、材料补充、人工审核完成和用户二次追问。
- **FR-014**: 系统 MUST 对开箱视频输出合规性结构化结果，包括一镜到底、未拆封快递盒及面单、剪辑疑似、商品离镜、瑕疵位置和置信度。
- **FR-015**: 系统 MUST 对商品损伤和发错货图片/视频输出证据链、置信度、SKU/订单比对结果和人工复核建议。
- **FR-016**: 系统 MUST 对未成年人退款材料做 OCR、脱敏、材料完整性、监护关系链和矛盾点检查，并保护身份证号、手机号、户口本、出生证明等敏感数据。
- **FR-017**: 系统 MUST 对第三方模型传入内容做最小化和脱敏；高敏证件原图默认不进入外部通用大模型。
- **FR-018**: 系统 MUST 提供质检 Agent，对客服 Agent 和人工回复进行 SOP 合规、情绪安抚、越权承诺、废话和风险话术检查。
- **FR-019**: 系统 MUST 提供质疑/主管 Agent，对“合理但超 SOP”的诉求生成特殊处理建议和审批依据。
- **FR-020**: 系统 MUST 支持 SOP 更新建议、人工审核发布、版本回滚和回归测试集同步。
- **FR-021**: 系统 MUST 支持私域企微社群消息接入、用户标签、商品推荐候选、主动触达风控和销售线索生成。
- **FR-022**: 系统 MUST 支持仓库任务收口、优先级、SLA、提醒、反馈同步和客服跟进建议。
- **FR-023**: 系统 MUST 提供成本观测，按文本、图片、视频、OCR、工具调用和人工转接统计调用量、失败率和单位成本。
- **FR-024**: 系统 MUST 提供 Mock 盲测流程，覆盖 SOP 分支构造样本、脱敏历史工单样本、在线聊天样本、视频/图片/证件 fixture 和异常路径样本。

### Non-Functional Requirements

- **NFR-001**: 用户可见首响在文本场景下 p95 小于 3 秒；需要后台查询或人工审批时必须先返回明确进度状态。
- **NFR-002**: P0 文本 SOP 盲测中，工单类型识别准确率不低于 90%，高风险动作误自动执行率为 0。
- **NFR-003**: 所有敏感操作审计记录包含租户、用户、坐席、会话、工单、订单、工具、请求摘要、审批人、结果和时间。
- **NFR-004**: 所有用户可见文案必须走 i18n，不允许在新增前端界面硬编码。
- **NFR-005**: 所有多端写操作必须可幂等重放，重复请求不得导致重复退款、重复补发或重复审批。

### Key Entities

- **用户**: 甲方会员，包含账号、手机号、实名状态、会员等级、历史售后、私域标签和隐私授权状态。
- **会话**: 一次多轮对话上下文，关联用户、入口、消息、Agent trace、风险状态和转VIP客服状态。
- **工单**: 客服处理单元，包含类型、状态、证据、SOP 分支、当前负责人、挂起原因和跨工单关联。
- **订单**: 商品购买记录，包含商品、金额、支付、物流、售后、退款和可操作状态。
- **SOP 知识单元**: 来自培训文档的版本化规则块，包含适用范围、前置条件、分支动作、话术和禁止项。
- **后台工具**: 可被 Agent 调用的只读或写入能力，带权限、审批、审计和回滚信息。
- **审核任务**: 需要人工、主管、答疑、仓库或财务处理的待办。
- **多模态证据**: 视频、图片、证件、流水、发票和用户补充资料，包含脱敏状态和模型分析结果。
- **质检记录**: 会话或回复的 SOP 合规、话术风险、越权承诺和改进建议。
- **私域线索**: 群消息、用户标签、商品兴趣、销售意向和人工跟进建议。
- **仓库任务**: 仓库核实、催发货、缺货、补货、物流异常和反馈同步任务。

## Success Criteria

- **SC-001**: P0 售后文本场景覆盖退款、物流、有伤、漏发、发错、未成年人退款、账号换绑，且每类至少 10 条 Mock/脱敏样本盲测通过。
- **SC-002**: 高风险写操作自动执行错误为 0，包括退款、补发、换货、拒赔、修改地址、账号换绑和未成年人退款终审。
- **SC-003**: SOP 检索结果必须展示来源文档和分支依据，业务验收人员能追溯到原 SOP。
- **SC-004**: 多端并发测试中，同一订单重复退款/补发/换货请求被幂等拦截，重复执行次数为 0。
- **SC-005**: LLM 失败、配额耗尽、模型超时和安全 block 均能在 3 秒内给出转VIP客服或待处理状态。
- **SC-006**: 未成年人退款材料审核中，敏感字段脱敏率为 100%，未经授权不得发送到外部通用模型。
- **SC-007**: 开箱视频和商品损伤审核以辅助质检上线，低置信度自动转VIP客服复核，不出现自动拒赔或自动赔付。
- **SC-008**: 质检抽样中，越权承诺、手算退款、泄露内部信息、未按 SOP 分支处理等风险可被系统标记并给出证据。
- **SC-009**: 私域试点社群能输出每日高意向用户、热议商品、负面情绪和人工跟进清单。
- **SC-010**: 仓库任务试点能记录任务创建、提醒、回复、关闭和同步用户跟进建议的完整链路。

## Scope

### P0 必须先做

- 文本 SOP 入库、版本化、检索和来源追踪。
- 售后 SOP 状态机：申请退款、物流异常、商品有伤初步、有开箱视频、漏发货、发错货、未成年人退款、账号换绑。
- Mock 业务接口契约：工单、订单、物流、售后卡片、退款状态、商品库。
- 工具调用权限、审批、审计、租户隔离和订单级幂等。
- 服务端权威会话历史、交接简报和多端并发锁。
- 安全审查前置、P0 转VIP客服短路、LLM 失败自动兜底。
- 基于 Mock/脱敏样本的盲测集与验收报告。

### P1 在 P0 之后做

- 开箱视频合规审核、商品损伤识别、SKU/订单图片比对。
- 未成年人退款 OCR、材料完整性与关系链辅助审核。
- 质检 Agent、质疑/主管 Agent、SOP 更新建议和版本回归。
- 事件触发跨天跟进和任务中心。

### P2 试点后扩展

- 企业微信私域社群接入、标签、商品推荐和销售线索。
- 仓库 Agent、催货 Agent、跨部门任务收口。
- 多模态成本优化、本地脱敏模型和更细的模型路由。

## Non-Goals

- 不在 P0 承诺全量自动赔付、自动拒赔、自动拉黑或自动修改后台关键数据。
- 不承诺接入甲方真实后台系统；本期验收以 Mock 业务闭环为准。
- 不把旧版 Companion/陪伴系统等同于客服 SOP 系统；当前主系统只保留“专业、同理、有边界”的客服服务人格。
- 不在没有真实样本的情况下承诺视频审核、损伤识别或证件审核准确率；Mock fixture 只能证明流程可走通。
- 不让第三方通用模型默认接触原始身份证、户口本、出生证明、手机号实名证明等高敏材料。

## Assumptions

- 甲方可以提供脱敏后的历史工单样本、SOP、在线会话样本、视频/图片/证件样本更好；如不能提供，本期由项目内构造 Mock 样本与固定 fixture。
- P0 阶段以“半自动处理 + 人工确认”为默认边界，先保证不越权、不重复赔付、不错误拒赔。
- Mock 写操作也必须经过权限矩阵和审批规则，避免演示逻辑与未来真实系统脱节。
- 多模态审核先用于辅助质检和人工复核，不直接作为最终赔付裁决。
- 私域运营和仓库 Agent 不阻塞客服 P0 上线。

## Current Implementation Gap

当前项目已具备：

- FastAPI + React 的五端入口。
- LangGraph 对话流程、情绪识别、转VIP客服、坐席台、运营台。
- SQLite auth/admin/handoff/review_task 存储。
- SSO、Chatwoot、Ops、E2E、联调实验室等工程基建。

当前项目未满足：

- `agent.py` 中 SOP 召回仍是硬编码摘要，未读取 `_extracted_sop`。
- 订单、物流、补偿和业务接口已有 Mock 雏形，但覆盖范围太窄，缺少工单、售后卡片、仓库、财务、商品库、企微、飞书等 Mock 契约。
- 开箱视频、商品损伤、发错货识别、证件 OCR 未实现。
- 未成年人退款状态机、材料审核和隐私脱敏未实现。
- 多端并发、订单级锁、跨工单重复赔付防护未形成生产闭环。
- 质检、质疑、SOP 自更新、版本回滚未实现。
- 私域企微、商品推荐、仓库 Agent 未实现。
- 当前流式输出、安全审查和转VIP客服顺序存在对抗性风险，需在 P0 前修复。
