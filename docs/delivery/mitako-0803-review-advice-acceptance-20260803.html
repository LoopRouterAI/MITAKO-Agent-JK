0803 反馈闭环

Agent 现在负责给明确建议，不再把“业务动作需甲方执行”误写成“每单必须人工”

本轮修复的是决策机制，不是单纯改报告文案。证据结论、SOP 处理建议、人工复核等级和业务执行权限已经拆开。

甲方指出的问题是成立的

旧版本一边要求 Agent 判断正负，一边又在核心提示词和结果守卫中强制 human_required=true。因此即使证据已经比较明确，也容易被统一写成“转 VIP 客服复核”。这会让 Agent 失去节省人工的商业价值。

现在一份结果分成四层

1. 证据结论

支持用户诉求、不支持用户诉求、证据无法判断。

2. SOP 处理建议

支持、不支持、安慰性补偿、补件或继续评估。

3. 人工复核等级

无需、建议抽检、必须复核。黄色风险不再自动升级为必须人工。

4. 业务执行权限

Agent 不直接退款、补发或拒绝。业务动作仍由甲方系统执行，但这不影响 Agent 给出明确建议。

本轮具体更新

场景旧行为新行为
商品有伤开箱条件不完整时倾向统一 review；提示词把“业务动作需人工”与“证据需人工”混在一起。按照版本化 SOP 输出支持或不支持倾向；只有证据冲突、关键材料缺失或系统处理未完成才保留 review。
安慰性补偿“补偿”字样会被守卫统一改写成转人工，事实结论也被冲淡。事实仍可明确为“不支持”，同时独立输出“可参考最低档安慰性补偿”，不声称已经执行。
未成年人资料五类材料齐全但有部分字段看不清时，整单仍显示待确认。材料齐全、无明确字段冲突、无阻断性修改风险时通过视觉初审；标黄项只供抽检，不要求逐张人工复核。
报告与 API“业务边界”容易被理解为 Agent 不敢判断。明确写为：Agent 负责证据结论和 SOP 建议；甲方系统负责执行；是否人工复核由独立字段决定。

API 关键返回示例

{
  "assessment": {
    "conclusion_code": "evidence_does_not_support_claim",
    "confidence": 0.82
  },
  "sop_recommendation": {
    "code": "comfort_compensation",
    "recommendation": "当前证据不支持用户诉求；补充证据可供最低档安慰性补偿参考。"
  },
  "human_review": {
    "level": "not_required"
  },
  "policy": {
    "business_action_allowed": false
  }
}

这个例子表达的是：Agent 明确认为证据不支持诉求，但按照 SOP 可以给安慰性补偿建议；Agent 不会自行付款，也不要求仅因为付款动作而转人工。
