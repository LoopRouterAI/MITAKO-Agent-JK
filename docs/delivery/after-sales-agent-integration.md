# 客诉审核 Agent 与沟通 Agent 接口联调指南

版本：2026-07-23

## 1. 交付形态

生产接入以标准 API 为主，演示网页为辅助。甲方订单、物流、工单、商品和用户系统不需要迁移到 MITAKO；甲方在客诉受理时冻结一份“本次审核证据快照”，调用审核服务异步获取结构化建议和可选 HTML 报告。

系统分为两条独立能力链：

1. 审核 Agent：读取案件材料、订单基准、物流/包裹、当前工单对话和媒体，输出事实证据结论、证据分数、信号及人工复审等级。
2. 沟通 Agent：现有 `/api/v1/chat` 独立承接最终用户消息、会话历史和图片附件，按甲方已批准 SOP 生成解释、补件或进度回复；它不直接执行退款、补发、换货或拒绝。

当前版本已经分别提供审核 API 和客服沟通 API，但尚未把某个 `job_id` 的审核建议自动注入某个客服会话。正式联调需要双方确定会话关联键、允许进入用户回复的公开字段、触发时点和人工审批规则；在此之前不得宣称两条链路已自动打通。

## 2. 推荐调用流程

1. 甲方客服系统创建客诉工单并生成 `client_case_id`。
2. 订单/商品/物流系统在同一时点生成版本化快照。
3. 甲方调用 `POST /api/v1/review/metadata/validate` 预校验字段。
4. 甲方以 `POST /api/v1/review/jobs` 提交一个案件及其全部图片/视频，使用稳定的 `Idempotency-Key`。
5. 服务返回 `202` 和 `job_id`；甲方轮询任务或在正式联调阶段接入双方约定的回调适配器。
6. 甲方读取 `job.result.review.advisory_assessment`。需要人读时再访问报告接口；纯系统消费可设置 `include_html_report=false`。
7. 甲方按自己的审批规则消费建议；审核服务永不直接执行售后动作。

批量任务采用“每个案件一个 job，共用 `batch_id`”。这保证单个坏文件不会拖垮整批，案件可以独立重试、计费、审计和查询。

当前 POC 运行时使用单机持久数据库、进程内工作池和周期性租约回收，可在进程异常后恢复到期任务；它不等同于跨节点持久消息队列。120GB 级批次或多节点生产扩容仍需在正式联调中接入甲方对象存储、外部任务队列和共享数据库，当前版本不伪装为已经完成水平扩容。

## 3. 场景数据契约

### 发错货

最低证据基准：

- `fulfillment_baseline.baseline_version`
- 应收商品的 `item_ref`、SKU 或可唯一识别组合、规格/款式、数量
- `packages[].expected_item_refs`，明确每个商品属于哪个包裹
- `evidence_coverage.submitted_package_refs` 或 `submitted_tracking_nos`
- 用户实际展示的包裹、包装标识、商品和开箱媒体

缺少包裹与商品映射时，服务仍可审核视频连续性和实际可见物，但不得输出确定的“发错货”事实结论。

### 漏发货

除应发商品外，还需要：

- 赠品、特典、套装组件和随机/盲抽规则
- 应发包裹数、拆单状态、每包应装商品
- 已提交证据覆盖了哪些包裹、运单和物品
- 物流是否全部签收；尚有包裹在途时不得直接认定漏发

视频未展示全部包裹或全部物品时输出材料缺口，不能把“没看到”直接等同于“漏发”。

### 商品有伤

SKU/官方图是增信信息，不是识别明显损伤或连续性的硬门槛。服务分别输出：

- 是否看见所投诉部位和损伤
- 商品、包装、争议部位是否持续可追踪
- 损伤更偏向开箱前、运输/包装、用户操作后或无法归因
- 离镜、遮挡、疑似剪辑等信号及时间点

离镜时长是证据强度信号，不单独证明调包或欺诈。默认 3 秒只触发补充连续材料建议，不直接拒绝。

### 未成年人资料

分三层输出，禁止混写：

1. 材料存在性：五类材料是否提交、是否清晰可读。
2. 字段一致性：未成年人、监护人、关系、订单、支付、手机号归属等字段是否在当前材料中互相一致。
3. 权威核验：身份证、手机号实名、订单和支付事实是否已由甲方权威系统验证。

“用户自述年龄”不能单独证明由未成年人完成了未授权购买和支付。审核 Agent 不决定是否退款，只给甲方客服提供证据与核验建议。

## 4. 当前工单对话

生产 API 可接收审核时点之前冻结的 `conversation_history`。只应传本案件当前阶段的用户陈述和必要客服追问，不要传人工最终结论、退款结果、评测标签或标准答案。

离线样本目录适配器不会读取 `reply.json`。只有人工明确准备的 `conversation_predecision.json` 才会作为当前阶段用户消息输入，并在送模前再次脱敏，以避免人工最终决定泄漏给模型。生产调用方应在源系统侧完成同等的阶段冻结和最小化处理。

## 5. 用户风险摘要

`customer_risk_context` 只允许传脱敏聚合统计，例如近 180 天售后次数、同场景次数和甲方已有风险等级。该字段只在服务端影响抽检优先级：

- 不发送给视觉模型；
- 不改变本次事实结论；
- 不允许触发自动拒绝；
- 不接收历史对话正文、手机号、证件号或其他身份明文。

## 7. 联调验收

- 契约：OpenAPI 可导入，metadata 校验能指出缺失字段。
- 幂等：同一案件同一请求重复提交不重复创建任务；内容变化时返回冲突。
- 隔离：人工标签和最终处理结果不能进入模型请求。
- 批量：同一 `batch_id` 下单案独立成功、失败和重试。
- 可观测：任务 ID、请求耗时、状态码、模型调用次数、Token/成本估算可追溯；日志不含凭证或媒体正文。
- 降级：ffprobe、官方图或某一模型通道不可用时明确标记，不伪装完整取证。
- 输出：JSON-only 与 HTML 两种模式均按契约返回。

## 8. 仍需甲方联调的真实接口

- 订单行、套装/赠品/抽赏规则和版本号
- 商品行与包裹/运单的真实映射
- 物流轨迹与签收状态
- 官方商品图/包装标识的受控读取地址
- 当前工单对话的冻结时点与角色映射
- 未成年人身份、手机号、订单、支付的权威核验结果
- 甲方客服审批动作、回调鉴权、对象存储和数据保留策略
- 审核 `job_id` 与客服 `session_id` 的关联、公开结论注入和回复审批规则

当前仓库提供契约、Mock/演示数据和可运行服务，但上述甲方真实系统尚未伪装为已接通。
