# 内部研发包交付说明

版本：2026-07-15

内部研发包用于我方 Java、Python、前端、测试、实施和运维交接，不得直接转发甲方或外部人员。

## 包内包含

- Git 当前提交中的完整源码、前端构建产物、启动与测试脚本。
- `我方内部开发文档/`、`docs/delivery/` 和甲方沟通材料。
- 当前 `.env` 与 `.env.example`。
- `data/` 下五个运行数据库的一致性快照。
- `data/chat_attachments/`、`data/private_domain_uploads/` 小型运行附件。
- `sample_002`、`sample_003`、`sample_004` 和视觉工作台轻量演示视频。
- `internal-package-manifest.json`，记录源码提交、数据库和排除项，不记录 Key 值。

## 不进入包内

- `.venv/`、`venv/`、`node_modules/`、`.git/`、`.codegraph/`。
- `tmp/`、`logs/`、缓存、历史测试输出和旧归档。
- `sample_001` 约 530MB 的原视频。
- `data/review_jobs/` 约 677MB 的历史审核附件。
- 甲方 120G 全量素材和其他外部数据盘文件。

大样本和历史审核附件应通过内网对象存储、共享盘或独立加密数据包交付，并恢复到原目录。不要通过普通 Git 或源码 ZIP 传播。

## 为什么拆成两个包

以前的单包同时承担内部开发交接和甲方演示，接收人、权限和安全边界不清晰。当前固定拆分为：

- `MITAKO_Agent-internal-dev-YYYYMMDD.zip`：仅限我方研发，包含源码、内部文档、当前环境配置和数据库快照。
- `MITAKO_Agent-customer-preview-YYYYMMDD.zip`：发送甲方，包含编译运行时、公开文档、OpenAPI、演示数据和工作台，不含环境凭证、数据库、源码、内部文档或盲测标签。

两个包的 manifest 都记录同一 Git 提交号和证据哈希，并由 `scripts/check_release_packages.py` 在全新目录解压后验证。拆包不是功能差异，而是最小权限、可追溯性和防止误发的发布工程要求。

## 打包与验证

先启动内部源码版主服务和视觉审核服务，然后执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/package_internal_release.ps1
```

脚本会先运行 `pre_release_internal_validation.ps1`。构建、服务健康、API、审核、客服、私域或文档校验任一失败时，不生成内部包。

当前门禁还会强制执行 0714 专项回归、前端用户/附件隔离、运行数据目录隔离和视觉工作台检查。涉及审核 Prompt、抽帧或模型路由的候选版应追加 `-RunModelBatch`。

内部包与甲方包都生成后，必须在全新临时目录解压、启动编译运行时并复跑私有化 API 冒烟：

```powershell
.\.venv\Scripts\python.exe scripts\check_release_packages.py
```

该脚本会校验两个包的文件边界、清单提交号、证据哈希、内部源码编译、甲方运行时冷启动、视觉服务健康和私有化 API 13 项检查。只有 `tests/reports/release_packages_latest.json` 中 `ok=true`，才允许发送。

## 安全要求

- 包内含真实环境配置和业务数据库，只能通过公司批准的加密通道发送。
- 接收人完成导入后应删除临时解压目录和传输副本。
- 禁止把内部包上传公开 GitHub、公开网盘、工单附件或即时通讯公共群。
- 对外演示仍使用 `MITAKO_Agent-customer-preview-YYYYMMDD.zip`。
