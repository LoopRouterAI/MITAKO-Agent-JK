## 本轮为什么修改

连续性审核曾按供应商类型选择两种媒体表达：部分通道使用独立 JPEG，部分通道把多帧压成 WebP 时序拼图。拼图适合人工快速浏览，但缩小后的局部细节、帧间映射和单帧证据强度不足以承担严肃审核，因此本轮将它从模型判定链路完全移除。

144989 真实回归还暴露了另一个聚合问题：系统把“材料已经提交”和“材料清晰到足以核验”混成一个状态。承诺书已被识别，但因部分可读被降成待确认，继而跳过全部字段一致性检查。本轮把存在性、质量状态和一致性状态拆开。

## 代码变更

- `poc/visual_review_poc/model_selection_e2e.py`：Gemini 原生与 OpenAI 兼容协议统一逐张发送 JPEG；忽略任何 `model_images_override`，每次连续性调用最多 24 张。
- `poc/visual_review_poc/specialized_model_pass.py`：删除时序拼图生成与回退分支；专项通道固定记录 `individual_frames`。
- 删除未进入报告展示链路的 `temporal_contact_sheet.py` 死代码。
- `review_service/service.py`：采样计划统一返回两个协议均为 `individual_frames=24`；契约明确原视频和拼图不进入模型审核请求。
- `poc/visual_review_poc/minor_material_pipeline.py`：材料 `status` 只表达是否观察到；新增 `quality_status` 表达清晰度/完整页风险。材料已观察但质量待确认时，仍继续运行五项字段一致性检查。
- `poc/visual_review_poc/workbench_server.py`：公开白名单允许非敏感 `quality_status`，仍过滤姓名、证件号、手机号、金额和 OCR 原文。
- `poc/visual_review_poc/report_assessment_sections.py`：HTML 分别展示材料状态、材料质量和验证状态。

## 配置与接口

```dotenv
REVIEW_CONTINUITY_FRAMES_PER_CALL=24
```

该值是上限，不是抽帧频率。抽帧频率继续由 `adaptive/strict/strong/custom` 控制；连续性分段只决定一次模型请求包含多少张独立帧。供应商不支持 Gemini Files URI 时，服务端以内联 Base64 发送 JPEG，不依赖文件 URI。

`POST /api/v1/review/sampling-plan` 当前会返回：

```json
{
  "continuity_frames_per_call": 24,
  "continuity_frames_per_call_by_transport": {
    "gemini_native_individual_frames": 24,
    "openai_compatible_individual_frames": 24
  }
}
```

## 部署注意

1. 同时重启主服务和视觉服务，避免主服务调用旧视觉进程。
2. 生产必须安装 ffprobe，并通过 `REVIEW_FFPROBE_PATH` 或系统 PATH 可执行。
3. Java 只调用主服务 `/api/v1/review/*`，不要直连视觉工作台内部接口。
4. `.env` 只进入内部研发包或部署 Secret；GitHub 和甲方测试包不得包含真实 Key。
5. 当前需要甲方提供身份、运营商实名、订单、支付和退款系统的测试接口，才能完成权威真伪与业务动作闭环。

## 剩余风险与下一入口

独立逐帧显著增加时延、Token 和结构化输出压力。当前安全策略是在模型漏帧时降级 `review`，而不是伪造完整结论。下一轮质量提升唯一入口是用甲方冻结标签的盲测集比较 12/24 帧分段、1/2 FPS 和候选模型的覆盖率、召回率、成本与时延，再确定生产默认档。
