## 匹配规则

同步工具 `scripts/sync_customer_order_info.py` 依次校验：

1. 工单目录名完全一致。
2. 场景一致：商品有伤、发错货、漏发货或开箱视频。
3. 标签一致：正/负或合格/不合格。
4. 目标唯一；多目标、无目标和场景冲突均不复制。
5. JSON 必须含非空 `goods_list`，每条商品必须有 SKU 身份、名称和正数数量。
6. 已存在目标文件时，相同哈希记为已同步；不同哈希记为冲突且不覆盖。

## 输入适配 Schema

`poc/visual_review_poc/local_video_triage_demo.py::order_info_context` 只输出：

```json
{
  "order_items": [{
    "item_ref": "ORDER-LINE-001",
    "sku": "SKU-001",
    "product_name": "商品名",
    "specification": "规格/款式",
    "expected_quantity": 1,
    "product_image_ref": "甲方商品图引用"
  }],
  "fulfillment_baseline": {
    "baseline_version": "order_info_snapshot:<sha256-prefix>",
    "expected_items": [],
    "source": "customer_order_info_snapshot"
  }
}
```

明确排除：`user`、`user_address`、收件信息、价格、人工标签和客服结论。商品图目前只是甲方路径引用；生产接入时由甲方商品库/API 返回可访问的签名 URL 或二进制，不在本轮伪造图片。

## 服务端策略边界

当前内置批准策略只有 `MITAKO-PD-MISSING-OPENING@20260717.1`。完整视频未见主诉损伤的自动判负仍是待甲方批准策略，不在默认注册表中。Java 请求中的阈值字段只作为契约兼容输入，服务端不会采用未批准覆盖值。

生产建议把批准策略迁移到受权限控制、带审计的租户策略表；变更必须经过客服主管、产品、法务和测试签署，不允许普通提交方写入。
