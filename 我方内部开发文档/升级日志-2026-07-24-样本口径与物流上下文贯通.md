## 有效结论摘要

1. `E:\AIGC\0 Mitako样本` 是我方研发数据源，不是运行时固定路径。测试脚本必须通过 `--sample-root`、`--samples-dir` 或调用方文件列表接收路径；甲方部署使用自己的路径或对象存储。
2. `annotation.json` 和 `reply.json` 中的人工终判只用于离线评测、标签复核和业务研究，不进入线上模型请求。
3. 线上推理可使用用户媒体、案件诉求、版本化订单/SKU 快照、明确的抽赏/特典规则、包裹物流和审核时点之前的最小化对话。
4. 一个物流单号不能证明未分包，多个物流单号也不能自动证明拆包关系。发错货和漏发货需要权威的包裹-SKU 映射；缺失时必须显式降级。
5. 正式审核 API 是甲方系统的唯一推荐入口；视觉工作台只用于 UAT、人工复测和报告查看。

## 真实样本字段口径

| 业务字段 | 可用来源 | 线上推理 | 说明 |
|---|---|---:|---|
| 用户诉求与媒体 | `content.txt`、manifest 资源、图片/视频 | 是 | 文件名和目录名先去除标签语义 |
| 订单行、SKU、数量、主图 | `order_info_snapshot.json` | 是 | 仅保留本订单相关最小字段 |
| 随机/隐藏/特典规则 | 订单快照中的明确规则 | 有条件 | 快照不完整时 `*_complete=false`，不得自行推断 |
| 包裹、物流、签收 | 甲方物流/履约快照 | 是 | 必须带来源与快照时间；包裹-SKU 映射需要权威关系 |
| 当前工单用户陈述 | 审核时点之前的最小化消息 | 有条件 | 禁止客服终判、退款结果和标准答案 |
| 正负样本、视频不合格原因 | `annotation.json` | 否 | 仅在模型完成后由评测器对比 |
| 人工最终售后决定、仓库终判 | `reply.json` 或业务记录 | 否 | 可整理离线标签，不得注入模型 |

数据目录包含多个批次、导出副本和重复工单。批量评测必须用稳定的工单/案件 ID 去重，批次路径只作为来源字段，不能以目录数作为独立样本数。

## 各场景工程判断

### 商品有伤

- 人工标注中的视频不合格原因适合作为回归标签。
- 线上伤情、离镜、遮挡、剪辑风险和损伤成因必须从本次媒体独立生成。
- SKU 详情和官方图用于正常材质、包装与款式参考；不能覆盖用户视频事实。

### 漏发货

- 应发清单来自版本化订单基线，实收/已展示清单来自媒体识别。
- 赠品、特典、套装和随机规则必须由业务快照明确提供。
- 单/多物流单号不能替代包裹-SKU 映射；尚有包裹在途或证据未覆盖全部包裹时不得形成确定漏发结论。

### 发错货

- 订单 SKU、规格/款式、数量与规则是应收基准。
- 用户媒体是实收证据；官方商品图是参考证据，不是用户已收到商品的证明。
- 人工最终标签只用于盲测对比。

### 未成年人资料

- 继续按材料存在性、跨材料字段一致性、甲方权威真实性核验三层输出。
- 订单快照并非该场景必需；身份、手机号、订单和支付真实性必须由甲方权威接口核验。

## 路径与部署要求

- 生产服务不得读取我方 `E:` 盘样本目录。
- Java/FastAPI 调用方从任意本地路径打开文件后以 multipart 上传；服务端以 `job_id` 存储，不保留调用方绝对路径。
- 大文件生产方案使用双方确认的对象存储引用与转码回调，当前 POC 不伪装已经接入。
- 内部样本命令示例统一使用 `$env:MITAKO_SAMPLE_ROOT`：

```powershell
$env:MITAKO_SAMPLE_ROOT = 'E:\AIGC\0 Mitako样本'
.venv\Scripts\python.exe poc\visual_review_poc\model_selection_e2e.py `
  --samples-dir $env:MITAKO_SAMPLE_ROOT `
  --models gemini35lite --sampling-mode adaptive
```

甲方环境可把该变量改为任意合法目录；正式 API 联调不需要设置此变量。
