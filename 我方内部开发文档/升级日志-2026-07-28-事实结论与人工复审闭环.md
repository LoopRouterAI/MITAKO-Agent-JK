## 最新记录入口：动态素材与统一审核链路

状态：当前有效

本轮在原有事实/责任/复审分层之上补齐五个工程闭环：

1. 单案资料容量改为软上限 40、默认安全上限 200；安全上限以内全部接收并分批处理，不再二次截断。
2. 技术批次未完成与用户材料缺失分开；前者输出 `technical_processing_incomplete + system_retry`，不要求用户重复上传。
3. 网页工作台和正式 API 复用 `postprocess_review`，输入完备性、分类策略、人工路由和报告口径不再各走一套。
4. 商品有伤默认使用版本化策略 `MITAKO-PD-ADVISORY@20260728.1` 输出事实建议；完整观察未见主诉伤情可以建议 `negative`，但不能自动执行经营动作。
5. 报告媒体通过 `/api/v1/review/jobs/{job_id}/media/{media_id}` 按任务鉴权代理；媒体索引使用 SQLite 持久化，服务重启后仍可解析已登记证据。

未成年人资料批次若供应商返回成功但遗漏图片编号，默认允许 2 次结构修复（总计最多 3 次批量调用）；随后仅对遗漏图片做逐张恢复。当前请求内仍未补齐才进入 `system_retry`。次数由 `REVIEW_MINOR_SCHEMA_RETRIES` 控制并纳入调用数、Token 与成本统计，最大值固定为 2。

若整批响应在结构修复后仍遗漏编号，只对遗漏图片执行逐张恢复，并复用同一重试上限；正常批次不增加调用。若调用任务重试接口，则会受控重跑整案并可能重复模型成本，本版本不宣称跨进程断点续跑。公开 Schema 已增加 `technical_processing_incomplete`、`not_applicable_processing_incomplete` 和 `system_retry`，避免任务完成后因新状态不在 Pydantic Literal 中而返回 500。

## 1. 反馈与根因

0724 版集中暴露了三类问题：审核结果普遍落在 0.5-0.7 并全部进入人工复核；报告不同区域对“是否复核”和“视频是否完整”给出矛盾信息；明确可见伤情会因为成因或商品连续性不确定而被覆盖成 `review`。

根因不是单一提示词过严，而是聚合层混合了四个不同问题：事实是否成立、成因与责任是否确定、是否需要人工复审、最终业务如何处置。报告又从多个局部对象取值，导致同一任务出现不同口径。

## 2. 代码修正

| 模块 | 修正 |
|---|---|
| `poc/visual_review_poc/damage_causality.py` | 分离可见伤情事实与形成原因；成因不确定不得覆盖明确伤情。 |
| `poc/visual_review_poc/object_continuity.py` | 连续性不确定作为独立风险；只在依赖连续性的自动分类规则中阻断。 |
| `review_service/advisory_assessment.py` | 将非阻断连续性信号降为 `optional`，保留服务失败、实质冲突和权威核验为 `required`。 |
| `poc/visual_review_poc/report_renderer.py` | 标题、事实、人工建议和流程建议统一读取 `advisory_assessment`；补件不再显示必须 VIP 复核；媒体状态转为人类可读文案。 |
| `docs/delivery/review-advisory-api.md` | 明确事实、责任、人工复审和业务处置四层契约。 |

补充图片只有在三项同时满足时才确认“可见伤情存在”：审核通道已采纳、证据置信度不低于 0.8、已建立同物关联。该规则不推断伤情形成时间或责任。

## 3. 输出与业务边界

- `positive`：当前证据支持事实诉求，不代表自动退款或平台责任。
- `negative`：当前证据不支持事实诉求或命中甲方已批准的材料规则，不代表自动拒绝。
- `review`：证据冲突或不足，不能被业务处置标签替代。
- `required / optional / not_required / request_more_material`：分别表示必须复审、可抽检、无需复审和先补材料。
- 最终退款、补发、换货、补偿或拒绝由甲方系统、SOP 与授权人员执行。

## 6. 部署与联调

1. 同一 Git 提交构建主服务与视觉服务，重启两个进程；主服务的 `VISUAL_WORKBENCH_PORT`/`VISUAL_WORKBENCH_URL` 必须指向该视觉实例。预发布曾用新主服务误连旧视觉实例，62 份素材被旧版 40 份上限截断，动态容量 E2E 已能拦截此类版本错配。
2. Java/业务系统只调用主服务 `/api/v1/review/*`，不要直接依赖内部视觉接口。
3. 先检查 readiness，再做单案、批次、JSON-only 和 HTML 四类请求。
4. 每个请求保留 `job_id`、`request_id`、策略版本、耗时、调用次数、Token/成本状态和失败原因。
5. 甲方路径不固定；调用方从任意本地路径或对象存储取得文件后上传，服务端不得依赖研发机 `E:` 盘。
