# 升级日志 · 2026-07-17 四样本审核工程

## 背景

甲方用 617341、614176、618205、617911 四个商品有伤样本复测。反馈确认 Strong 强化抽帧方向有效，同时指出普通档漏检离镜、ffprobe 未部署、部分可判负场景仍转人工、614176 多阶段诉求混杂，以及 Strong 报告出现局部分段时间矛盾。

## 本轮代码升级

- 商品有伤 `adaptive` 不再使用 6-24 帧粗筛，默认执行 1 FPS 主审、主体连续性和损伤成因三通道质量底线。
- `strong` 统一为 2 FPS、最多 1800 帧；`strict` 保留 1 FPS；`custom` 继续支持 0.1-2 FPS。
- 分段 Prompt 明确“分段末帧不等于视频结束”。公开结论改由完整帧注册表、专项连续性和全局时长确定性聚合。
- 新增 `global_review_summary` 与 `aggregation_warnings`，局部声称结束但后续仍有证据时强制转 `review`。
- 新增版本化 `claim_scope`，每个原子诉求可绑定商品、部位、首次提出回合和证据；614176 的初始娃娃品控诉求与后增撕拉片诉求不再混为一个标签。
- 新增默认保守的 `decision_policy`。617341 只有在甲方批准的版本化策略明确“商品有伤必须有开箱视频，缺失时分类为 negative”时才输出规则性不支持；该结论不会伪装成视觉证明无伤。
- “完整视频未见伤”判负必须同时满足：诉求部位明确、同物关联、主张部位特写、必检视角 100% 覆盖、无冲突证据、零允许离镜、连续开箱与置信度阈值。617911 当前缺部位特写，因此保持 `review`。
- 规则覆盖后同步更新 `summary`、`agent_brief`、`overall_audit` 和 `decision_policy_audit`，修复标签与人类可读正文矛盾。

## 部署与稳定性

- 新增可构建 `Dockerfile`，镜像安装 ffmpeg/ffprobe；`docker-compose.yml` 补齐主服务、视觉工作台、Redis、worker 和持久化卷。
- `REVIEW_FFPROBE_PATH` 支持固定可执行路径；Windows 开发机可运行 `scripts/setup_ffprobe_windows.ps1`。
- `/api/v1/review/readiness` 检查 ffprobe、上传目录写权限、三倍案件上限磁盘水位和视觉工作台连通性。
- 新增 `deploy/nginx/mitako-review.conf.example`，审核入口基线为 800MB、关闭请求缓冲、上传与读取超时 1800/1900 秒。
- 内部工作台 429/502/503/504 做有限重试，每次重开文件流并记录状态码、耗时和重试次数。

## 真实验证

- 618205 原视频：71.633 秒，ffprobe 容器、音视频流、帧率和 2147 个视频包时间轴检查完成。
- 614176 原视频：602,861,197 字节、240.433 秒，真实 ffprobe 检查完成，探测耗时低于 4 秒。
- 第一轮正式 API 盲测成功捕获内部工作台瞬时 503，随后据此新增有界重试；该失败没有被隐藏或改写成业务 `review`。
- 盲测输入仅包含中性文件名媒体、`content.txt` 原始诉求和本次审核策略，不上传 `annotation.json`、`reply.json`、`manifest.json`、人工结论或目录标签。

## 边界

- `negative` 是审核分类建议，不自动拒绝、退款、补发、换货或定责。
- ffprobe 风险信号只表示需要复核，不证明视频被剪辑或篡改。
- 甲方 Java 网关、对象存储、七牛云转码和真实工单回写仍待双方联调，当前只提供契约、Mock 与部署基线。
