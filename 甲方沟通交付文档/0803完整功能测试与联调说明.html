先说本轮最重要的变化

Agent 可以给明确的审核倾向，不再因为“退款等动作由甲方执行”就把每个案件都推给人工。

一份结果现在分为四层：证据是否支持用户诉求、按照 SOP 建议怎样处理、是否需要人工复核、业务系统是否执行退款或补发。前两层由 Agent 给出建议，最后一层仍由甲方控制，两者不再互相干扰。

更细的测试证据见交付包内《0803 审核建议验收说明》和《审核结果字段说明》。

五分钟启动

  1. 解压 ZIP，确认电脑已安装 Python 3.11 或更高版本，并保持网络可用。
  2. 双击 start-windows.bat。第一次会安装运行依赖，后续启动会更快。
  3. 浏览器自动打开用户客服页面。人工客服工作台为 http://127.0.0.1:8000/desk，运营后台为 http://127.0.0.1:8000/admin。
  4. 视觉审核工作台使用包内 visual_review_workbench/start-workbench-windows.bat，地址为 http://127.0.0.1:7861/。
  5. 若端口已被其他程序占用，启动脚本会明确报错，不会静默切换到其他端口。

建议按这六条路线测试

1. 用户客服

连续发送订单、退款、投诉和图片/视频相关诉求，观察上下文是否连续、敏感问题是否升级、转人工后是否保留摘要。

2. 人工客服协同

从用户页面触发转人工，再到工作台查看会话、意图、情绪和最近诉求；人工服务期间继续发消息，右侧分析应同步变化。

3. 运营后台

查看任务、风险、运行状态和私域模块；切换演示用户时，不应看到上一位用户的订单焦点。

4. 单案视觉审核

提交一个工单文件夹。系统应忽略隐藏和无效文件，读取订单资料、图片与视频，完成审核并生成报告。

5. 批量审核

通过网页批量工单或标准接口提交多个案件，逐案查看任务状态、结论、置信度、耗时和错误，不应因单个坏文件拖垮整批。

6. 私域 Agent

使用演示群消息和商品事件观察分群、运营候选、风险禁推和转客服任务。真实群聊和商品事件仍需联调。

四类审核分别看什么

场景主要判断依据报告应给出的结果
商品有伤开箱连续性、商品是否离镜、视频中的伤情、补充图片、订单与商品资料证据是否支持伤情、SOP 倾向、关键画面、疑点和复核等级
发错货订单商品/规格/数量、官方参考、用户实际展示物品、随机或特典规则收到物与订单是否一致、未确认项目和证据时间点
漏发货应发清单、实际展示清单、赠品规则、包裹和分包物流信息疑似缺少的商品/数量、已识别项目、未覆盖项目和置信度
未成年人资料五类材料是否齐全、可读、字段是否相互一致、明显修改风险视觉初审倾向、每类材料状态、黄红风险图片和下一步建议

系统输出审核建议，不会在测试环境中自行执行退款、换货、补发或拒绝。

报告颜色和人工复核怎么读

绿色

证据和规则已达到当前配置门槛，可给明确倾向；甲方可直接采用或按比例抽检。

黄色

存在非阻断疑点。报告会说明看哪里，不代表必须把整单从头人工重审。

红色

关键证据冲突、明显风险或处理失败，建议授权人员重点复核原始证据。

置信度不是历史准确率。它表示本案证据对当前结论的支持强度。生产准确率仍需用双方确认的盲测集统计。

接口联调怎么开始

  1. 先访问主服务的 /docs 或使用交付包内 docs/delivery/openapi.yaml 查看接口契约。
  2. 甲方系统提交案件、附件地址或批次；服务返回任务编号，调用方按任务编号查询状态和结果。
  3. 调用方可只取结构化字段，也可选择生成 HTML 报告。Java 示例见 docs/delivery/java-client-sample.md。
  4. 重点读取证据结论、SOP 建议、置信度、人工复核等级、风险信号和错误信息，不要只读一个总状态。
  5. 正式联调时再替换演示数据来源，接入订单、商品、物流、客户和企业通信系统。

哪些是真实能力，哪些仍是演示

类别当前状态
页面、接口、单案/批量任务、审核报告、客服转人工链路可运行、可测试

退款、换货、补发、拒绝等最终业务动作由甲方规则和授权系统执行，本服务只给建议和证据
生产准确率与节省人工比例需在冻结标签的黄金样本集上独立统计，不用文件夹名称暗示答案

功能
