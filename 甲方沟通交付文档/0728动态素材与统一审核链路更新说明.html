0728 交付更新

多资料不再被截断，网页和 API 使用同一套审核结论

本轮处理的不是单纯“把模型调得更敢下结论”，而是修正资料接收、分批处理、结论聚合和报告访问四条工程链路。目标是让同一案件无论从网页还是正式 API 提交，都能完整处理、解释一致、可追溯。

适用：商品有伤、发错货、漏发货、未成年人资料版本：2026-07-29性质：审核建议，不直接执行售后处置

之前真正的问题是什么

0727 反馈中“置信度普遍偏低、全部不确定、未成年人图片处理不全、报告图片打不开”并不只是提示词保守。更直接的原因是：单案资料在不同层被重复限量，网页和正式 API 的后处理不完全一致，内部处理失败又被误写成用户缺材料，浏览器还拿到了只能在服务器内部访问的媒体地址。

资料被截断

上传成功不等于全部进入分析。旧链路存在第二次限量，62 张资料可能只处理其中一部分。

失败被误解释

系统没有处理完时，旧报告可能要求用户补材料，导致“资料明明在，却说缺失”。

两套结论链

网页和正式 API 经过的校验与建议生成不同，可能出现同材料不同口径。

本轮实际更新

01 接收清点全部资料记录接收数、软上限和安全上限
02 处理动态分批40 份以内标准处理，41-200 份扩展处理
03 聚合全部批次再下结论任何未完成批次都不会伪装成证据结论
04 建议统一网页与 API事实、置信度、复审等级来自同一对象
05 报告任务级媒体访问帧图和视频通过主服务安全返回
动态上限的含义：40 不是拒收线，而是正常处理软上限。默认安全上限为 200；安全上限内全部接收并分批聚合。超过上限时明确返回 HTTP 413 和收到数量，不静默少审。部署方可根据机器、时延和成本评测调整。

结论如何使用

输出人话含义建议用法
positive现有证据支持本次事实诉求可按甲方规则继续，不等于自动退款
negative完整审查后证据不支持诉求，或命中已批准材料规则可作为客服事实建议，不等于自动拒绝
review证据冲突、关键基准缺失或事实无法确定人工复审或按报告补齐明确缺口
system_retry当前请求完成结构修复和逐张恢复后，仍有资料未被完整处理可受控重跑整案，可能重复模型成本；不要求用户重传，达到重试上限后再转授权人员
商品有伤已启用版本化事实建议规则：清楚看到伤情可建议正；视频与补充证据完整、覆盖主诉位置但仍未见伤情时可建议负；存在实质冲突才复审。离镜、遮挡和轻度媒体风险是证据权重信号，不单独证明调包或欺诈。

甲方如何复测

  1. 同一案件分别从网页和 POST /api/v1/review/jobs 提交，核对事实结论、置信度、人工等级和流程建议一致。
  2. 提交 40 份以内和 41-200 份的未成年人资料，核对接收数、已处理数和分类汇总；不得出现“已上传但未处理完却要求用户补件”。
  3. 商品有伤分别测试：清楚可见伤情、完整观察未见伤情、证据冲突三类案件，预期分别覆盖正、负、复审，而不是全部转人工。
  4. 打开 HTML 报告并查看关键帧、问题时间点和原视频预览；浏览器不应再请求服务器本机地址或内部工作台端口。
  5. 用同一幂等键重放请求，确认任务 ID 不变；服务重启后再次打开报告媒体，确认索引可恢复。

正式 API 可选择只返回结构化字段，也可为每个案件生成 HTML；生产批量仍推荐“一案一任务、同批共用 batch_id”。

明确边界

本服务输出证据事实、未校准证据分、风险信号和人工建议，不直接执行退款、补偿、换货、补发或拒绝。企微、CRM、订单/库存、仓库核验、对象存储与未成年人权威真伪接口，仍需甲方提供测试环境和契约后联调；当前演示数据不能冒充真实接入。

主服务与视觉执行器现在会校验版本、素材容量、固定签名密钥和运行目录可写性；内部后处理控制只接受主服务共享密钥，报告媒体 API 已明确支持图片、视频与 Range 分段读取。甲方部署只需对外暴露主服务 API，视觉执行器保留在内网。

本轮工程修复可以解决“少审、错把系统失败当缺件、网页/API 不一致、报告媒体失效”等问题，但不能替代黄金样本集。生产准确率仍应由双方冻结的样本、审核时点输入和事实标签进行盲测评估；最终 ZIP 内机器报告会记录对应 git_commit，用于确认 62 份资料验收确实来自包内代码版本。
