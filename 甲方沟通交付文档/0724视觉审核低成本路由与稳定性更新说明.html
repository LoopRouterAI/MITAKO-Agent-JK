MITAKO 售后审核 Agent
功能、测试方法与真实联调边界

这份说明回答四个问题：本轮究竟改了什么、当前一共能做什么、甲方应该怎样测试、哪些能力仍需接入甲方真实系统。正式业务接入以标准审核 API 为主，网页用于 POC 验证、人工查看证据和复测。

四类售后审核 单案与异步批量 JSON / HTML 可选 订单、SKU、包裹物流上下文 标签隔离

先说结论

审核服务可以作为独立 API 进行甲方联调。甲方不需要使用我们的网页来录入订单，也不需要直接调用内部模型服务。甲方按案件提交业务 JSON 和图片/视频，服务异步返回结构化审核建议、置信度、证据链、人工复审等级和可选 HTML 报告。网页工作台保留给测试人员和客服查看报告，不是生产订单录入系统。

本轮实际更新

01

包裹物流进入真实审核上下文

修复正式 API 已接收物流 JSON、但内部视觉链路只保留文本状态的问题。包裹状态、包裹引用和商品归属现在能进入统一证据包，供发错货、漏发货对账使用。

02

样本答案与线上推理严格隔离

annotation.json 和客服最终处理记录仅用于离线评测与业务复核，不进入模型请求。线上只读取用户证据、订单快照、明确的商品规则和审核时点之前的必要对话。

03

部署路径不再绑定研发电脑

样本根目录由命令行参数或部署配置传入；正式 API 使用上传文件、案件 ID 和后续约定的对象引用。甲方可以使用自己的 Linux 路径、对象存储和目录结构。

04

保留低成本路由与稳定性能力

审核模型、超时、重试、并发和抽帧强度继续由服务端配置；失败通道可受控回退，任务记录耗时、调用次数、Token/成本状态和失败原因，公开报告不暴露凭证或内部提示词。

真实样本字段应该怎样使用

研发理解核对结论正确用法
商品有伤的视频不合格原因、人工伤情意见来自标注与客服记录部分正确适合整理离线评测标签，不得把人工结论送入模型。线上伤情等级必须由本次媒体证据独立判断。
商品特殊规则来自 SKU 详情、活动或抽赏规则正确只传本订单相关且可解释的规则；历史快照不完整时标记规则未齐，不擅自补全。
漏发货应发清单来自订单，实收清单来自用户媒体正确还要提供赠品/特典、套装组件、包裹数和证据覆盖范围，服务才能做履约对账。
一个物流单号代表未分包，多个物流单号代表分包不能这样推断物流单号数量不能证明包裹与 SKU 的归属。需要甲方订单/仓储系统给出权威的包裹-SKU 映射；缺失时输出证据不足或复核建议。
仓库核实结论、发错/漏发事实标签来自标注和客服记录仅限离线评测可由业务人员离线整理为评测标签，但线上模型请求不能读取；生产事实应来自仓储核验接口或本次证据。
随机、隐藏、特典和款式规则来自订单商品详情有条件正确以版本化规则为准。只有订单快照明确记录且与本订单商品关联时才可用于确定判断。

甲方怎样测试审核服务

1. 检查服务读取健康、就绪和审核契约，确认媒体工具、任务存储和必需配置可用。
2. 校验案件先提交 metadata 校验。发错/漏发应带版本化订单基线、包裹映射和证据覆盖。
3. 创建任务每个案件一个异步 job，同批案件共用 batch_id；不要把 120GB 素材塞进一个请求。
4. 读取结果轮询任务，优先消费结构化建议；需要人读时再打开 HTML 证据报告。
  1. 正式入口：主服务 /api/v1/review/*。内部视觉端口不对甲方业务系统开放。
  2. 单案：验证同一个幂等键不会重复创建任务，图片和视频都能进入同一案件。
  3. 批量：每案独立提交、共用 batch_id，验证部分失败不阻塞整批。
  4. 盲测：文件名、目录名、请求 JSON 和对话不得包含正负标签、人工最终结论或标准答案。
  5. 输出：分别测试 JSON-only 与 JSON + HTML；核对结论、置信度、证据帧、材料缺口和复审等级。
  6. 路径：甲方可从任意目录读取文件后上传。服务不要求出现 E:\AIGC\0 Mitako样本，该路径只是我方研发数据源。
